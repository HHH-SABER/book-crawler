# 反爬库选型评估与优化清单 (2026-09-02)

> 基于当前代码库现状 (`请求引擎.py` / `browser_driver.py` / `反爬检测器.py` /
> `captcha_module.py` / `风控事件.py`) 与 8 站 + xingguangks 实测, 回答两个问题:
> 1) 要不要再引入成熟反爬库? 2) 现有程序还有哪些该升级、按什么顺序做。
> 结论先行见 §3。

---

## 1. 现有技术栈盘点 (代码事实)

| 层次 | 现有实现 | 成熟度 |
|---|---|---|
| 请求层 | requests(默认) + **curl_cffi(TLS 指纹模拟+HTTP/2)** + **cloudscraper(自动 JS 质询)** 三引擎自动降级, 按域名缓存会话 | 高 |
| 浏览器 | playwright(主) + selenium(回退), 内置 **stealth 脚本**(去 webdriver 标记) + `--disable-blink-features=AutomationControlled` | 高 |
| 反爬识别 | `反爬检测器`: 按状态码+文案识别 rate_limit/ua_block/waf_js_challenge/blocked, 产出建议策略 | 高 |
| 验证码 | 5 策略: ddddocr OCR / slider(cv2) / point_click(多模态) / third_party / **manual 兜底**, 含监控 | 高 |
| 退避 | 指数退避 + Retry-After 尊重 + **域级冷却(跨 run 持久化, P2-3)** | 中高 |
| 调度 | 断点续传 + 多源回退 + threads 并发 + 质检 | 中高 |
| 解析 | sites_config 配置驱动 + 分发器 + 解码链(码点流/Base64/实体) + 14 容器兜底 | 高 |
| 监控 | 风控事件 JSONL + monitor_summary 聚合告警 + GUI 健康度(P2) | 中(刚建) |
| **代理** | **仅单点 `request_proxy` 字段, 无池、无轮换、无失败切换** | **低(短板)** |
| **指纹治理** | TLS 层已伪装; **浏览器级指纹/UA 会话池缺失**(固定 UA 为主) | 中 |

## 2. 目标站点特征 (实测分级)

| 反爬强度 | 站点 | 机制 | 现状 |
|---|---|---|---|
| 弱 | oldtimeswx / 322zw / shubaoks | 频率限速为主 | 直连可达, 全过 |
| 中 | 630wang / yipinzongshi / orion34g / ltbook | 数据混淆(qsbs_bb/码点流/有损数字替换) | 已解, 全过 |
| 中强 | xingguangks | 分卷结构 + 偶发 520/522 + 首包 JS 质询 | 已适配, 全过 |
| 强 | tanmixs / banlvzw(m) | selenium/数据文件 + WAF | 已适配, 全过 |

**关键判断**: 目标站点以"数据混淆 + 频率限速 + 偶发 JS 质询"为主, **几乎没有需要大规模代理池的硬 IP 封禁**; 现有 8/8 通过、124 章 0 失败即是证明。

## 3. 结论先行

**不建议引入额外成熟反爬库**。原因: 主流库的核心能力(TLS 伪装、浏览器 stealth、JS 质询、验证码)本项目**已经等价自建**, 再引入是能力重复, 只会增加维护面、资源占用与不稳定因素。真正的增量价值不在"再堆一个库", 而在 **代理治理 / 指纹会话池 / 调度与自适应 / 监控闭环** 四项工程短板。

## 4. 主流反爬库逐一对比

| 库 | 绕过检测 | 并发性能 | 维护成本 | 稳定性 | 对本项目结论 |
|---|---|---|---|---|---|
| **playwright** | 强(反检测上下文+网络拦截) | 中(浏览器重) | 低(官方活跃) | 高 | ✅ 已在用, 维持 |
| **selenium** | 弱(webdriver 标记明显) | 中 | 低 | 高 | ✅ 已在用(回退), 不升为主动 |
| **undetected-chromedriver** | 强(专门 patch chrome) | 中 | 中(随 chrome 版本被动) | 中 | ❌ 不引入: 等价于已有 playwright+stealth; selenium 仅是回退位, 为其加 stealth 收益≈0 |
| **pyppeteer** | 中 | 中 | **高(年久失修)** | 低 | ❌ 不引入: 是 playwright 的降级替代, 维护最差 |
| **curl_cffi** | 中(TLS/HTTP2 伪装) | 高(纯 HTTP) | 低 | 高 | ✅ 已在用, 维持; 建议确认 `impersonate` 参数已启用 chrome 指纹 |
| **cloudscraper** | 中(自动 JS 质询) | 中 | 低 | 中 | ✅ 已在用(降级链) |
| **crawlera 等商业代理** | 强(住宅 IP 池) | 高 | 中(订阅成本) | 高 | ⚠️ 非库是服务: 只有出现硬 IP 封禁时才值得, 当前站点不需要 |

**综合**: 已引入的 curl_cffi + cloudscraper + playwright + selenium 四件套, 恰好覆盖了 undetected-chromedriver / pyppeteer 所补的那一块; 再引入属于重复建设。

## 5. 引入成本收益量化 (估算)

| 方案 | 开发 | 部署 | 维护/月 | 资源 | 收益 | 净结论 |
|---|---|---|---|---|---|---|
| 引入 undetected-chromedriver | 0.5天 | 低 | +1h(版本跟随) | +50MB/实例 | 成功率 ≈ 0(已有 playwright) | **负收益** |
| 引入 pyppeteer | 1天 | 中 | +4h | +80MB | 成功率 ≈ 0 甚至降 | **负收益** |
| 引入 crawlera 住宅代理 | 1-2天接入 | 中 | ¥数百~数千 | 无本地 | 仅硬封 IP 场景 +10~30% | **按需, 当前非必需** |
| **自建代理池(见§6-1)** | 2-3天 | 中 | 低(自维护) | 无 | 同场景 +10~20% | **优先于商用(可控+省)** |
| **指纹会话池(见§6-2)** | 1-2天 | 低 | 低 | 无 | 限速/UA 封禁场景 +5~15% | **性价比最高** |

## 6. 优化升级清单 (按优先级)

> 实施建议以"低风险、可单测、不破坏主链路"为原则; 预期效果为相对当前基线的增量估计。

### P0-1 代理池管理 (补齐最大短板)
- **现状**: 单点 `request_proxy`, 无轮换/失败切换/健康检查。
- **实施**: 建 `代理池.py`——多代理列表 + 按域分配 + 失败标记降权 + 冷却; 对接请求引擎; 保留"直连优先"默认(当前站点多数无需代理)。
- **预期**: IP 封禁场景成功率 +10~30%; 平时零开销。**条件**: 有可用代理源时才启动。

### P0-2 请求限速与重试自适应
- **现状**: 指数退避已有, 但限速是静态 `delay`, 重试档位固定。
- **实施**: 用 `风控事件` 的 rate_limit 事件驱动——某域 24h 命中≥阈值时, 自动下调该域默认 delay(如 ×2), 冷却后恢复; 重试策略纳入 `Retry-After` 精确值。
- **预期**: 减少"反复触发限速→被封"的恶性循环, 稳定性提升, 无成功率损失。

### P1-1 指纹/UA/会话池
- **现状**: TLS 已伪装, 但浏览器级指纹与 UA 基本固定。
- **实施**: UA 池(按域名绑定, 会话内不变, 跨会话轮换) + playwright 上下文指纹参数化(时区/语言/视口/Canvas 扰动轻量做); 首包重试换 UA 已存在, 扩展为"会话级固定"。
- **预期**: UA 封禁场景成功率 +5~15%; 注意别过度随机(反而暴露)。

### P1-2 任务调度与异常恢复增强
- **现状**: 断点续传 + 多源回退已有。
- **实施**: 失败章节自动重试队列(有限次+指数间隔); 单章超时杀线程(防卡死); 崩溃后自动从 checkpoint 续传的提示。
- **预期**: 大任务稳定性 +, 尤其慢站点/网络抖动。

### P1-3 监控闭环收尾 (P2 已打底)
- **现状**: 事件打点+聚合+告警+域冷却已建。
- **实施**: 告警落地到 GUI 通知(非仅 CLI); 24h 报告定时生成; 命中率纳入打包前回归看板。
- **预期**: 从"被动翻日志"到"主动发现", 运维效率 +。

### P2-1 curl_cffi impersonate 显式化
- **实施**: 确认并显式指定 `impersonate="chrome120"` 等, 避免默认指纹; 加一个 TLS 指纹冒烟测试。
- **预期**: 堵住"已装 curl_cffi 但未真正用其指纹"的可能盲点, 成本极低。

### P2-2 站点适配持续化
- **实施**: 用已交付的 `probe_adapter.py` 把新站接入变成"探测→草稿→确认", 配合 replay 回归; 建立"站点改版告警"(正文容器/混淆特征漂移时提示)。
- **预期**: 接站时间 -60% 以上; 改版导致的静默失败率大幅下降。

## 7. 一句话总结

**当前项目在"单站精细适配 + 数据解码 + 基础反爬对抗"上已达到成熟商用爬虫的 80% 水准, 且已经引入了关键反爬库(curl_cffi/cloudscraper/playwright); 继续引入 undetected-chromedriver/pyppeteer 属于重复建设, 不建议。** 真正的护城河缺口是"规模治理三件套"(代理池 / 指纹会话池 / 自适应限速) 与"运维闭环"(监控告警), 按 P0→P2 顺序补, 即可用最低成本把成功率与稳定性再抬一个台阶。
