# 浏览器插件配套方案 —— 可行性评估与实施建议

> 2026-10-20 · 针对现有爬虫（多引擎 + Flet GUI + 远控）的配套浏览器插件
> 结论先行：**可行，且本项目的地基（远控 FastAPI / 验证码接管窗口 / 域 COOKIE 注入）
> 恰好是插件方案的三个挂点**。建议分三期实施，第一期（凭据中继）性价比最高，
> 1.5 天可交付。

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 可行吗 | 可行。插件与爬虫通过本机 HTTP（复用远控服务）协作，零新增基础设施 |
| 补什么 | 登录态/Cookie、JS 渲染、验证码人工闭环、交互加载——四类纯 requests 引擎的天花板 |
| 不补什么 | IP 层封锁（如 bbbiquge 连接拒绝——浏览器在你 IP 下同样连不上）、站点真死 |
| 与 selenium 引擎的关系 | **不是替代，是新增"真人浏览器引擎"**——寄生在日常浏览器里，WAF 最难分辨 |
| 成本 | 一期 1.5 天（凭据中继）；全部四期约 6-8 天 |
| 风险 | MV3 休眠、需浏览器在线、不上商店（开发者模式加载）——均有对策 |

## 1. 现状盘点：插件要补的缺口（全部来自实测）

现有爬虫已有的反反爬能力：requests / curl_cffi / cloudscraper 三引擎轮换、
selenium/playwright 兜底、js_cookie 反爬处理、验证码自动识别 + **人工接管窗口**
（连续失败转人工，captcha_module）、域级 COOKIE 注入、DoH 回退、速度自适应 +
站点冷却、多源回退、R05 地址安全。

实测暴露的四个天花板（纯 HTTP 引擎无论如何调优都过不去的）：

| # | 缺口 | 实测案例 | 为什么 HTTP 引擎过不去 |
|---|---|---|---|
| G1 | JS 挑战型 WAF | washai 风控页《WAF 安全防御系统》被当目录页 | Cookie 由 JS 算出，requests 拿不到 |
| G2 | 限频致死 | task_22 在 washai 反复退避重试，进度极慢 | IP+指纹被标记，换引擎同 IP 无解 |
| G3 | 验证码人工闭环缺失 | 接管窗口只是"冷却等待"，人在哪点验证码没有出口 | 无真实浏览器会话可接管 |
| G4 | 交互加载 | 部分站点"点击加载更多/无限滚动" | requests 只有首屏 HTML |
| — | IP 封锁（对照） | bbbiquge 连接拒绝 | **插件也无解**（同 IP 连接层不通），需换网络/代理 |

## 2. 插件补什么（逐项方案与依赖）

| 缺口 | 插件做法 | 用到的浏览器 API | 爬虫侧改动 |
|---|---|---|---|
| G1 登录态/Cookie | `chrome.cookies` 读取目标域的全部 Cookie（含 HttpOnly/JS 算出的）→ 推送爬虫 COOKIE 库 | `cookies` + `alarms`（定期刷新） | 零改动——`注入COOKIE()` 现成管线直接吃 |
| G1.5 WAF 通行证 | 人在浏览器里正常访问一次目标站（WAF 放行）→ 插件自动收割通行 Cookie | 同上 | 同上 |
| G2 限频分散 | 高价值站点的部分章节由插件在浏览器里抓（真人指纹，限频阈值远高于爬虫 IP） | `scripting`/`fetch` in page context | 章节队列分发接口 |
| G3 验证码接管闭环 | 爬虫进接管窗口 → 推事件给插件 → 插件自动开目标页标签 → **人点一下验证码** → 插件收割通行 Cookie 回传 → 爬虫退出接管继续抓 | `tabs` + `cookies` | 接管窗口状态接口（`接管状态()` 已有，补推送） |
| G4 JS 渲染/交互 | content script 等待渲染完成/模拟滚动后抽取正文 DOM → 回传 | `scripting.executeScript` | 正文管线接收"预渲染 HTML"（跳过提取，直接清洗） |

## 3. 协作架构

```
┌─────────────────────────────── 用户日常浏览器 ───────────────────────────────┐
│  浏览器插件 (MV3)                                                            │
│  ├─ background (service worker): 轮询/长连爬虫 API, 任务分发与回传            │
│  ├─ content script: 目标站页面内抽取渲染后 DOM / 注入轻量交互脚本             │
│  └─ popup: 手动"为当前站点推送 Cookie"按钮 (P1 的可见入口)                    │
└──────────────┬───────────────────────────────────────────────────────────────┘
               │  http://127.0.0.1:<远控端口>/api/v1/ext/*   (Header: 远控 token)
               ▼
┌─────────────────────────────── 爬虫 (大脑) ──────────────────────────────────┐
│  远控服务 (FastAPI, 已存在) ── 新增 /ext 组:                                  │
│    POST /ext/cookies   凭据上报 → 写入域 COOKIE 库 (注入COOKIE 现成消费)      │
│    GET  /ext/tasks     领取"浏览器引擎队列" (需要真人环境的 URL 清单)          │
│    POST /ext/content   回传渲染后 HTML → 交正文管线 (跳过提取直接清洗)        │
│    POST /ext/captcha   接管结果回传 (通行 Cookie + 截止时间)                  │
│  请求引擎 ── 新增引擎档 "browser_ext": 站点策略连续失败时按回退链挂到链尾       │
│  captcha_module ── 接管窗口事件 → 推给插件 (复用 接管状态())                   │
│  调度/解析/存储/断点/质检/多源回退 ── 全部不动 (插件不碰这些)                  │
└──────────────────────────────────────────────────────────────────────────────┘
```

三条数据流：

1. **凭据流**（P1）：插件 → `/ext/cookies` → COOKIE 库 → 三引擎自动受益
2. **内容流**（P2）：爬虫发 URL 队列 → 插件在真实浏览器抓 DOM → `/ext/content` 回传 → 正文管线
3. **接管流**（P3）：验证码事件 → 插件开标签 → 人解决 → `/ext/captcha` 回传 → 退出接管

## 4. 数据传递方式对比（为什么选复用远控 HTTP）

| 方式 | 安装成本 | 实时性 | 双向 | 依赖浏览器开着 | 结论 |
|---|---|---|---|---|---|
| **本机 HTTP（复用远控 FastAPI）** | 零（服务已存在） | 轮询 1-3s 或 SSE | ✅ | 插件侧天然在线 | **✅ 一二期采用** |
| Native Messaging | 高（需装 native host + 注册表/manifest） | 高 | ✅ | ❌ 不需要 | 三期后再评估（脱机场景才需要） |
| WebSocket | 中 | 最高 | ✅ | 插件侧在线 | 可作为 HTTP 轮询的升级项 |
| 文件交换 | 零 | 差（轮询文件） | ✅ | ❌ | 否决（并发/脏读难管） |

安全边界：`/ext/*` 只绑 127.0.0.1 + 校验远控 token + Cookie 上报按域白名单
（只收用户在插件里明确添加的站点），杜绝"任意网页借 localhost 打进爬虫"。

## 5. 职责划分（关键纪律：插件不做脑子的活）

| 职责 | 归属 | 理由 |
|---|---|---|
| 任务调度、章节解析、清洗、质检、断点/事务写、多源回退、限频策略 | **爬虫** | 全部既有管线，插件重复实现=两套状态必然漂移 |
| 目标站 Cookie/登录态提供 | **插件** | 只有真实浏览器有 |
| JS 渲染后 DOM 提供 | **插件** | 只有真实浏览器有 |
| 验证码"人"的那一半 | **人 + 插件** | 插件开标签、人解决、插件收割 |
| 解析规则适配（html_selector 等） | **爬虫**（站点配置/适配器） | 插件只送 HTML，不做站点特化 |
| 数据落盘 | **爬虫** | R04 事务写 / 断点 / 去重，插件不碰文件 |

## 6. 成本与局限

### 成本（纯开发，不含测试机验证）

| 期 | 内容 | 插件侧 | 爬虫侧 | 合计 |
|---|---|---|---|---|
| P1 | 凭据中继（Cookie 推送 + popup 手动入口 + 白名单管理） | 1 天 | 0.5 天（/ext/cookies + 站点白名单存储） | **1.5 天** |
| P2 | 渲染外送（URL 队列分发 + DOM 回传 + 正文管线接入） | 1.5 天 | 1 天 | **2.5 天** |
| P3 | 验证码接管闭环（事件推送 + 开标签 + 回传联动接管窗口） | 1 天 | 1 天 | **2 天** |
| P4 | 交互抓取（滚动/点击脚本编排） | 2 天 | 0.5 天 | 2.5 天（建议后置，性价比最低） |

### 局限（如实列出）

| 局限 | 影响 | 对策 |
|---|---|---|
| MV3 service worker 空闲 ~30s 被杀 | 长抓取期间长连不稳 | 轮询模式 + `chrome.alarms` 保活；任务粒度拆小 |
| 需要浏览器开着且插件在线 | 不在线时该引擎不可用 | 爬虫按站点策略把插件引擎当**回退链一环**，不可用自动降级回原引擎——**爬虫永不被插件绑架** |
| 开发者模式加载（不上 Chrome 商店） | 首次安装需开开发者模式；商店政策对爬虫类不友好，**不上架** | 打包 zip + 一页安装说明；EXE 旁放 `插件/` 目录随包分发 |
| 浏览器自动化本身可被指纹检测 | 理论风险 | 插件寄生在**用户日常浏览器**，指纹即本人——这正是它比 selenium 强的地方 |
| 法律/站点条款 | 与现有爬虫同一边界 | 仅个人学习研究使用；插件不抓取用户未明确添加的站点（白名单硬约束） |
| IP 层封锁无解 | bbbiquge 类连接拒绝 | 插件也无解（同 IP）；需代理/换网络，属另一议题 |

## 7. 与现有 selenium/playwright 引擎的关系（诚实对比）

| 维度 | selenium/playwright（已有） | 浏览器插件（新增） |
|---|---|---|
| 浏览器 | 独立启动的干净实例 | **用户日常浏览器**（真实指纹/登录态/历史） |
| WAF 识别难度 | 高（自动化特征多） | 低（就是真人浏览器） |
| 登录态 | 需手工注入或重登 | 天然自带 |
| 前置条件 | Chrome + 驱动（已自动管理） | 浏览器开着 + 插件已装 |
| 稳定性 | 会话生命周期可控 | 依赖用户浏览器状态 |
| 定位 | 兜底引擎（无人值守可跑） | **真人环境引擎**（兜底链末端的攻坚手） |

结论：两者互补。无人值守长跑靠现有引擎；单站反复被 WAF/验证码卡死时，
把该站的回退链尾挂上插件引擎，由"真人在场"的会话啃硬骨头。

## 9. 实施建议（明确到决策）

1. ~~**先做 P1 凭据中继（1.5 天）**~~ ✅ 已完成（见 §8）——爬虫侧几乎零改动
   （`注入COOKIE()` 现成），对 js_cookie 类反爬（实测已出现）立竿见影。
   交付物：插件 zip + `/ext/cookies` 端点 + popup 手动推送入口。
2. **P2 渲染外送（2.5 天）**：解决 G1/G4，死书与连续失败站点自动受益；
   与 R04 事务写/断点管线天然兼容（回传的 HTML 走同一正文管线）。
3. **P3 验证码接管闭环（2 天）**：把"接管窗口"从冷却等待变成真实闭环，
   是验证码体验的终极形态；建议在 P1/P2 验证稳定后再上。
4. **P4 交互抓取后置**：等前三期跑出真实数据，确认剩余缺口再决定。
5. **触发策略**：`站点配置` 每站新增 `引擎回退链` 字段，默认
   `requests → curl_cffi → cloudscraper → (selenium) → 插件`；
   插件不在线时自动跳过——**任何情况下不影响现有抓取**。
6. **不建议**：Native Messaging（安装成本高、P1/P2 用不上）、上 Chrome 商店
   （政策风险）、让插件承担解析/存储（职责纪律）。
