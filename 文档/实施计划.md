### ✅ C7 分发形态评估（2026-10-17 完成）：维持便携 + 轻量更新检查，不引入安装器

**现状事实（评估基线）**：
① 分发 = GitHub Release 单文件 EXE（~290MB onefile）+ sha256 + 站点适配器 zip，手动下载替换；
② 数据层已是**双模式**：`便携模式.flag`（数据/日志随 EXE 走）vs 默认 `%LOCALAPPDATA%/小说爬虫`；
③ **桌面快捷方式首启自建**（`gui_components/首次引导.py`，含 OneDrive 重定向处理，有测试）；
④ 版本号 GUI 可见（窗口标题 / EXE 版本资源）；
⑤ **无任何更新机制**——新版本要靠人自己去 Release 页下载替换。

**三选项对比**：

| 选项 | 收益 | 成本 / 风险 | 判断 |
|---|---|---|---|
| A 维持便携（现状） | 零安装摩擦；CI 已就绪；U 盘即用 | 无更新提示 | 基础盘，保留 |
| B 引入安装器（Inno/MSI） | 开始菜单项、卸载条目、"正式感" | CI 加工具链；升级/卸载残留回归；**不解决更新**；290MB 安装器只包同一 EXE | **不推荐** |
| C 便携 + 轻量更新检查 | 补上唯一真痛点（知道有新版本） | 一个只读模块 + 侧栏一行 | **推荐（已落地）** |
| D B+C | 以上全部 | B 的全部成本 | 过度工程 |

**推荐 C 的理由**：安装器的传统三大收益里，快捷方式（首启自建）与"开始菜单等价物"
已被更轻方案覆盖，卸载条目对"自己+弟弟+少数朋友"的分发场景价值低；而安装器
**不解决更新**这个真痛点。人数少、分发集中（GitHub Release）、用户技术 proximity 高——
安装器的边际收益趋近于零，成本却是实打实的工具链与回归。

**落地内容**（提交 `c7` 见 git log，模块 `源码/更新检查.py` + 测试 `测试/test_更新检查.py` 14 例）：
- 侧栏底部版本行：常态"检查更新" → 后台线程只读 GitHub `releases/latest`；
- **两态交互**：查到新版 → 行文变"⬆ vX.Y.Z 可用"并 SnackBar 告知；**再点一次**才用
  系统浏览器打开发布页（网络副作用要用户点头，不自动开浏览器）；
- 版本比较按**数字段**（2.5.10 > 2.5.9）；任一侧解析不出 → 不提示；
- 任何失败（离线/超时/限流/坏 JSON）→ None + debug 日志，**绝不抛**；
- **不在启动时自动检查**（零网络意外）；不下载、不静默替换——更新动作永远在人手里。

**明确不做**：安装器（B/D）；启动时静默检查；自动下载替换（安全边界——替换可执行文件
必须由用户在 Release 页确认后手动完成）。

### 待实施提案 · 输出文件名兜底值退化（2026-10-07 发现；**2026-10-08 v2.5.1 已实施文件名部分**）

> **状态更新（2026-10-08）**：**文件名部分已实施** —— 书名退化时输出名改为
> `未识别书名_<域名>_<路径段>.txt`（新增 `书名退化集合` / `_书名已退化` / `_从URL取书标识`,
> 与 `死书处理` 同口径, 并有回归用例守两处漂移）, 见 CHANGELOG `[2.5.1]`。
> **仍留一项**：`书名退化集合` 这组字面量同时被"死书判定"与"文件名回退"复用,
> 两处语义耦合(改动时容易互相误导) —— 是否拆成"判定用哨兵"与"展示占位"两个概念待评估;
> 当前用"同口径断言"兜住。

**问题**：书名解析失败时，程序的书名兜底集合是字面量
`书名退化集合 = (None, '', 'novel', '小说')`（`源码/死书处理.py`），而**输出文件名是由
"书名"拼出来的** → 落成 `novel.txt` / `小说.txt` 这类不可读的名字。

**实测证据**（2026-10-07）：`dist/抓取结果/novel.txt` 是一本真抓下来的 5.47 MB 书
（77 个章节行，首行 `## https://<站点>/<书号>/index.html`）；同一 URL 另有
一份**书名解析成功**的副本（1.24 MB / 24 章节行）。两者同源但不等同。

**为什么值得修**（不只是"名字难看"）：
1. 名字不可读，用户无法判断这是什么书；
2. **破坏去重**：同一个 URL 抓两次会得到两个不同名的文件，按名去重失效，
   只能靠内容指纹兜底（这正是上面那份 5.47 MB 与 1.24 MB 并存的原因之一）；
3. `novel` 这个名字本身还会被 `死书处理` 当作"书名退化"信号 —— 文件名与判定信号
   共用同一个字面量，二者的含义耦合在一起，容易在改动时互相误导。

**正解方向**（未选型）：输出文件名回退顺序改为
`解析出的书名 → 网站清单.txt 里该 URL 的书名 → URL 末段 → 兜底占位`，
让占位值**只用于判定**、不再直接当文件名；并在文件名里保留可辨识后缀
（如短 hash）以同时避免同名互相覆盖。

**验收要点**：造一份"书名解析失败"的离线样本，断言输出文件名**不含** `novel`/`小说`
字面量、且同一 URL 重复抓取得到**同一个**文件名；`死书处理` 的退化判定不受影响。
