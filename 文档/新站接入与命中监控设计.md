# 新站接入与命中率监控落地设计 (2026-09-02)

> 目标: 把"每接一个站都要人工开荒适配"和"被限速/封禁了才发现"这两件事,
> 从纯手工变半自动。设计完全贴合本仓库现有架构, 分阶段可落地。
> 关联: 文档/SITE_ADAPTER.md (模式库), 文档/项目审查报告-2026-09-02.md,
> 源码/sites_config.py, 源码/反爬检测器.py, 源码/site_probe.py。

---

## 1. 现状盘点 (写设计前先认清家底)

| 能力 | 已有实现 | 缺口 |
|---|---|---|
| 站点测试连接 | `site_probe.probe_site(url)` → {状态码/耗时/引擎/反爬识别} | 探测结果不落盘、不与 SITE_PATTERNS 建议关联 |
| 反爬识别 | `反爬检测器` 按 状态码+文案 → 建议策略 (retry_after/rotate_ua/use_selenium/cooldown) + 证据 | 结果只即时使用, 不聚合、不统计、不告警 |
| 抓取历史 | 爬取历史.py: 新增/更新/未变化/失败/哈希去重 | 无"按站点聚合的命中率/风控事件"维度 |
| 内容质检 | 内容质检器: 章节级评分 | 无"空正文/过短/清洗杂质"的站点级趋势 |
| 日志 | B1 后全量落盘 日志/*.log (带级别/来源) | 无结构化事件流, 监控只能靠翻文件 |
| 站点适配 | SITE_PATTERNS 配置化 + 分发器 + 解码链 + clean 链 + 测试快照回归 | 新站配置靠人工归纳, 无辅助生成器 |

结论: **"引擎"已经很强; 缺的是"接入辅助"和"运行观测"两端。**

## 2. 阶段一: 新站探测辅助 (`脚本/probe_adapter.py`)

目标: 贴一个 URL, 输出一份 **可直接抄进 SITE_PATTERNS 的适配建议草稿**。

### 2.1 探测流程 (对照七层纵深逐层判定)

```
输入 catalog_url
 ├─ L1 请求层: requests 直达 → 状态码/耗时/是否 403/429/522/520
 ├─ L2 头层  : 空 Referer vs 带 Referer/UA 是否变化; 是否需 cookie(js 质询)
 ├─ L4 渲染层: 正文容器是否在原始 HTML (关键词命中 目录/章节 候选?) → 
 │             "渲染?" 需 inspect(无头浏览器) 才能见到 → 判定 dynamic
 ├─ L5 混淆层: 正文容器内是否含 qsbs.bb/base64/initTxt/码点流/脚本 eval 特征
 ├─ 目录形态 : 收集 a[href] 分布 → 输出候选 chapter_url 正则 + 分页/分卷模式
 └─ 正文形态 : 候选容器文本量 + 行结构 (p/br) + 页眉污染 (广告/书名作者行)
输出 JSON 建议 { domain, pattern, content_selectors, chapter_url_regex,
                  content_extractor 建议, pagination, 是否需专用 parser }
```

### 2.2 与现有代码的衔接

- **复用**: `site_probe.probe_site` (连接测试)、`反爬检测器.识别` (首包反爬判定)、
  现有 `extract_content_html_selector` 的 14 容器兜底 (作为"正文容器自动定位")、
  `content_decoder.detect_data_refs` (混淆探测)。
- **新增**: 一个把探测证据 → SITE_PATTERNS 草稿的聚合函数 (纯函数, 可单测)。
- **验收标准**: 对 测试样本/ 里 8 个已知站点回放, 生成建议与原配置一致率 ≥ 80%,
  不一致处输出差异供人工确认 (把"测试样本回放"作为 probe 的离线回归)。

### 2.3 输出示例

```json
{
  "domain": "xingguangks.com",
  "pattern": "html_selector",
  "catalog": "分卷式(目录页/part/{id}/ → /list/{id}/{n}.html 分卷链, 需专用 parser)",
  "content_selectors": ["div.content", ".content", "#content"],
  "content_extractor": "xingguang_filter(建议: 剥离'阅读模式'提示行 + '书名作者'前缀)",
  "pagination": "无(每卷单页)",
  "anti_spider_hits": ["偶发 520/522"]
}
```

## 3. 阶段二: 命中率监控 (运行观测)

### 3.1 事件源 (零新采集, 从现有输出聚合)

把已散落的信息变成**结构化事件**, 统一追加到一个 JSONL: `数据/风控事件.jsonl`
(append-only, 按天轮转)。事件类型与现有产出映射:

| 事件 | 触发点 (改造成本极小) | 关键字段 |
|---|---|---|
| `request` | 请求引擎每个响应 | 域名, 状态码, 耗时, 引擎 |
| `anti_spider` | 反爬检测器.识别 命中非 200 | 域名, 类型(rate_limit/waf/blocked), 建议策略 |
| `captcha` | 验证码模块 `_record` | 域名, 类型, 结果(命中/人工/成功) |
| `content_issue` | 质检/正文过短/空章 | 域名, 类型(empty/short/fingerprint) |
| `task_result` | run_crawl 收尾 (已有爬取历史) | 域名, 新增/失败数 |

### 3.2 聚合与展示 (轻量)

- `脚本/monitor_summary.py` → 输出近 24h 表:
  - **按域**: 请求数 / 非 200 率 / 验证码率 / 空正文率 / 失败章数
  - **阈值告警**: 非200率 > 15% 或 验证码率 > 20% 或 连续失败>N → 打标 ⚠
- GUI「站点管理页」扩展一列"今日健康度" (读同一聚合), 不做常驻后台;
  需要实时时再考虑轮询。

### 3.3 自动退避联动 (最有价值的一步)

监控识别到某域 rate_limit/blocked 时, 不是只告警, 而是:
- 写回该站点的 `建议策略` 缓存 (retry_after/cooldown),
  `run_crawl` 启动时读取 → **全站自动降速或暂停该域**。
- 现有 `反爬检测器` 已产出建议策略, 缺的是"**跨请求的域级状态**" —
  一个 `数据/域状态.json` (域名 → 冷却截止/当前限速/失败计数), 供引擎查询。

| P1-1 | probe_adapter.py: 探测脚本(单 URL 命令行) | 复用 site_probe/检测器 | 0.5-1天 | 手动跑 xingguangks 输出合理草稿 |

| P2-1 | 风控事件 JSONL 写入点(5 类事件挂钩) | — | 0.5-1天 | 跑一次任务产生事件行 |

> 全部完成约 4-5 个工作日, 可穿插在正常迭代中; 每一步都不动现有抓取主链路。

## 5. 设计原则 (防止变成"为了监控而监控")

1. **零新采集**: 事件从已有请求/检测/历史点派生, 禁止为监控加第二套抓取。
2. **旁路不阻塞**: 事件写入失败绝不影响抓取 (与 日志.py 同策略)。
3. **可回放可测**: probe 生成配置与 monitor 聚合都是纯函数/脚本, 用样本回放做回归。
4. **写回闭环**: 告警 → 域状态 → 引擎退避 → 恢复, 形成一个圈, 而不是只出一张表。
5. **合规内嵌**: 所有自适应都做"降速/礼貌化"方向 (尊重 Retry-After/限速),
   不做任何绕过访问控制的激进策略。
