### S1. `源码/爬虫.py` 6,554 行单文件 + `gui_app.py:main()` 1,043 行

- 新增适配器/引擎时要在大海里找插入点。

**修复方案**（分 Wave，1418 测试 + 门禁守着，可安全推进）：

```
源码/爬虫.py（6554 行）
  └→ 拆为包 src/爬虫包/  （或保持单文件先拆函数，二选一，见下）
```

推荐**两步走**而非一次性搬家（Karpathy：精准修改）：

- **Wave 1（低风险）**：文件内先做"提取函数"——把 `main()` 按职责切成
  `_解析命令行参数() / _交互式菜单() / _按模式分发()` 三个 ≤150 行函数，
  `run_crawl()` 的 13 参数收进 `CrawlOptions` dataclass（见 S2）。
  纯文件内移动，不动调用方语义。
- **Wave 2（中风险）**：把 `爬虫.py` 按职责拆成 `爬虫核心.py`（调度/线程）、
  `章节抓取.py`、`内容清洗.py`（若尚未独立）、`质检.py` 等，每个 ≤800 行；
  每拆一个模块跑一次全量门禁，红即回滚。

**收益**：单文件修改的定位成本从"全文件"降到"单模块"。

### S2. `run_crawl()` 13 个位置参数（过长参数列表）

**位置**：`源码/爬虫.py:5886`

```python
def run_crawl(catalog_url, mode="full", sort_chapters=True, output_dir=None,
              resume=True, show_progress=True, chapter_range=None, threads=None, delay=None,
              stop_event=None, unique_title=False, export_epub=False, incremental=False,
              txt_indent=None):
```

**影响**：13 个参数全部是位置敏感的可选项——调用方（CLI 交互菜单、任务管理器、协议唤起、增量更新）任何一处参数顺序写错就是**静默行为错误**（类型相同不报错）。

**修复**（可直接落地）：

```python
from dataclasses import dataclass, field

@dataclass
class CrawlOptions:
    mode: str = "full"
    sort_chapters: bool = True
    output_dir: str | None = None
    resume: bool = True
    show_progress: bool = True
    chapter_range: tuple | None = None
    threads: int | None = None
    delay: float | None = None
    stop_event: object | None = None
    unique_title: bool = False
    export_epub: bool = False
    incremental: bool = False
    txt_indent: bool | None = None

def run_crawl(catalog_url: str, opt: CrawlOptions | None = None) -> None:
    opt = opt or CrawlOptions()
    ...
```

调用方从 `run_crawl(url, "full", True, None, True, ...)` 变为
`run_crawl(url, CrawlOptions(mode="range", chapter_range=(5, 20)))`——
**关键字传参，顺序错误在语法层就消除**。改动期间保留旧签名的兼容包装（
`def run_crawl_legacy(*args, **kwargs)` 内部转 Options）可让 1418 测试零修改通过，
下一Wave再清理。

### W2. `请求引擎._域COOKIE` 热更新存在极小窗口竞态

**位置**：`源码/请求引擎.py:45`（`_加载域COOKIE`）

```python
_域COOKIE.clear()
_域COOKIE.update({...})
```

**影响**：多线程抓取时，30 秒热检若正好落在 `clear()` 与 `update()` 之间，
该瞬间的请求会**漏注入 Cookie**（表现为偶发一章 403/空内容，重试可过）。
概率低但真实存在（插件每 2 分钟推一次 Cookie，会触发热检）。

**修复**（3 行，语义等价）：

```python
_新表 = {str(k).strip().lower(): str(v) for k, v in _data.items() if k and v}
_域COOKIE.clear()          # 保持原引用（其他线程已持有）
_域COOKIE.update(_新表)
```

更彻底的做法是整体替换引用（`_域COOKIE = _新表` 需改读取处为函数调用），
上面这个"先算完再换"已消除 99% 窗口，成本最低。

### W3. 68 个模块级可变全局中约 12 个是跨模块可变缓存

**证据**：`sites_config.py` 8 个（`SITE_PATTERNS`/`ADAPTERS`/`_广告规则缓存`/`_EXTRACTORS`…）、`插件安装.py` 7 个（探测表）、`ui_tokens.py` 7 个（主题色表）、`dns_doh.py` 3 个（含 `_doh_cache`）。

**说明**：其中大部分是**只读常量表**（dict 字面量配置，无风险）；
真正会写的是 `_域COOKIE`（W2）、`_doh_cache`、`_广告规则缓存` 三个。
GIL 下 dict 单键写入安全，但"清空+重填"模式不安全（W2 同款）。

**建议**：给这三个补一个统一的"缓存替换助手"（先构造新对象、再原子换引用/update），
并在模块 docstring 标注"该全局由 X 在 Y 时机写入"。

### W5. `dist/` 内混入浏览器 profile 运行时产物（48 个 `.old` 文件）

**证据**：`dist/站点适配_本地/browser_profile_7ku/…LOG.old` 等——
