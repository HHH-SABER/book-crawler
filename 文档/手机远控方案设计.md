# 手机远控方案设计(方案 B 优化版 v2)

> 2026-09-09 定稿。选定功能组合:① 在线阅读页 + ③ 面板下载 + ④ 完成推送;
> 底座:常驻机 + FastAPI 服务层 + Tailscale 内网。
> 本版对 v0 草案(直接写 NiceGUI 面板)做了六项关键升级,见第三节。

## 一、目标与范围

- 手机/外部设备可:发任务、看实时进度、读已抓的书、下载 EPUB、任务完成收推送
- 常驻机(家里 PC/NAS):跑抓取本体,反爬火力全开,断点续传常驻
- 不做:公网暴露、多租户、手机本地跑抓取(备选的 Termux 本地方案已于 2026-09-09 移除,当前唯一移动端方案即本方案)

## 二、总体架构

```
┌─ 常驻机 (远控服务, 独立进程, 开机自启+看门狗) ──────────────┐
│                                                            │
│  爬虫核心 (现有, 不改行为): TaskManager + NovelSpider      │
│      │ 事件总线 (新增): task_started / chapter_progress /  │
│      │               task_terminal  (线程安全队列→订阅者)   │
│      ▼                                                     │
│  FastAPI 层 (新增, /api/v1):                               │
│   POST /tasks  GET /tasks  GET /tasks/{id}/logs (SSE)      │
│   GET /books   GET /books/{id}/epub                        │
│   GET /books/{id}/chapters[/{n}]   POST /progress          │
│   GET /healthz                                             │
│      │                                                     │
│  消费者:                                                   │
│   ├─ NiceGUI 面板 (发任务/列表/日志/书架/下载)              │
│   ├─ 移动阅读页 (轻 HTML, 排版/翻章/进度)                   │
│   ├─ 完成推送器 (Bark/ntfy, 订阅 task_terminal)             │
│   └─ (预留) Bot 入口                                       │
└────────────────────────────────────────────────────────────┘
        ▲ Tailscale + tailscale serve (HTTPS, 免公网IP)
   手机浏览器 / Legado(WebDAV 可选) / Bark / ntfy
```

组件职责边界:爬虫核心不改行为;事件总线是唯一的"爬虫→外界"信息通道(替代
print 正则解析);FastAPI 层是唯一事实入口;三个消费者都是"皮"。

## 三、关键变更说明(v0 草案 → v2)

| # | 变更 | 理由 |
|---|---|---|
| 1 | "NiceGUI 直接包业务" → **FastAPI 事件总线 + 面板纯展示** | 面板/bot/推送共用同一事实;避免第二套前端逻辑漂移(项目已有前科) |
| 2 | GUI 1s 轮询 → **事件总线 + SSE 流式日志** | 实时性毫秒级;正式解决审计反复点名的"print 正则数据通道" |
| 3 | 服务与 flet 桌面 GUI 的关系明确为**互斥运行**(启动脚本加进程锁),长期让 flet GUI 也降级为 API 客户端 | TaskManager 是进程内对象,两进程各起一份会任务列表分裂;数据文件本身安全(原子写+防抖) |
| 4 | 安全从"tailnet 内网即信" → **token 认证 + 默认只绑 Tailscale 网段(100.64/10)双保险** | Web 服务是新增攻击面;推送链接需要长期可点,单独发长 token |
| 5 | 部署从"手动启动" → **NSSM 注册服务(崩溃自动拉起)+ /healthz 看门狗** | 远控的价值=常驻,进程死了没人拉就失去意义 |
| 6 | 服务重启任务列表不丢:启动时从 书架.json/checkpoint **只读恢复展示**,中断任务标 `interrupted` | TaskManager 内存态,重启即失忆会让"远控"不可信 |

## 四、改进点与预期效果

| 改进点 | 内容 | 预期效果 |
|---|---|---|
| 事件总线 | TaskManager 内加线程安全发布器,三个生命周期事件 | 日志实时毫秒级;print 正则通道退役路径成型;多消费者零成本接入 |
| SSE 日志流 | GET /tasks/{id}/logs 用 Server-Sent Events 推增量 | 手机上看日志不再整页刷新,流量小 |
| 结构化回调(顺带清遗留) | 爬虫侧 TaskEvent 回调注入 TaskManager | 审查报告 M11 的"文案契约"测试退役为兼容层 |
| EPUB 按需生成 | GET /books/{id}/epub 现调 epub_exporter,产物缓存(txt mtime 失效) | 不占双份磁盘;下载按钮即点即得 |
| 在线阅读页 | 独立轻 HTML(非面板控件):分章接口/字号/日夜间/下一章预取/服务端进度(按 token) | 手机排版可控;换设备进度跟人走 |
| 完成推送 | 订阅 task_terminal → Bark(iOS)/ntfy(安卓),消息含 书名+阅读链接+下载链接+质检摘要 | 任务完成主动找人;链接点开即读/即存 |
| 只读恢复 | 服务启动扫 书架.json+checkpoint 重建任务展示,running 标 interrupted | 重启后状态可信 |
| 磁盘治理 | 书架页显示占用+删除;EPUB 缓存按 mtime 失效 | 常驻机磁盘不失控 |
| 配置外置 | 数据/远控配置.json:端口/token/推送密钥/绑定网段 | 敏感项不进代码,换机只搬数据目录 |

## 五、安全设计

1. 默认监听 `127.0.0.1` + 经 `tailscale serve` 反代出 tailnet;或直接绑 100.x 网段;**绝不 0.0.0.0**
2. 面板/阅读/下载全走 Bearer/cookie token(首次启动生成,存远控配置.json)
3. 推送里的链接带长有效期的 `?k=` 参数(与 token 等权,泄漏即换)
4. 发任务 URL 强制过 `validate_public_url`(复用爬虫现有 SSRF 防线)
5. 下载/章节接口按书架 id 索引映射文件路径,杜绝路径穿越

## 六、部署与运维

- Windows 常驻机:NSSM 注册 `python -m 远控服务`(或任务计划开机启动),进程退出自动重启
- `/healthz` 供外部看门狗;服务自身日志接入现有 日志.py(按天轮转/30 天清理)
- 升级流程:git pull → 重启服务;数据目录与代码目录分离,升级不动数据
- 前置条件:常驻机装 Tailscale(手机同账号);Python 环境(见风险 1)

## 八、风险与权衡

| 风险 | 影响 | 对策 |
|---|---|---|
| Python 3.14 生态:FastAPI/NiceGUI/pydantic 对 3.14 的兼容未验证 | 服务起不来 | 常驻机独立 venv 先验;不行就用 Python 3.12 独立环境跑服务(爬虫代码本身 3.10+ 兼容) |
| 服务与 flet GUI 同跑会任务列表分裂 | 状态混乱 | 启动脚本进程锁互斥;文档写明;长期统一到 API |
| 常驻机断网/停电 | 远控失联 | Tailscale 只解决寻址;接受"机器不在线=服务不可用",推送器可加失联心跳提示 |
| Bark 点击链接需手机 tailnet 在线 | 弱网点不开 | 文档说明;或链接走 ntfy 自建(同 tailnet) |
| 新 Web 面的维护成本 | 双前端漂移 | 面板只做最小集(四件事),全功能仍在桌面 GUI |

## 九、最终建议

1. **按一期→三期顺序实施,总计 4~6 天**;一期结束即获得"手机发任务+看进度+下载"的可用闭环
2. 事件总线/结构化回调作为第一步先行——它同时清偿审计遗留项,且是 ①④ 与将来 bot 的公共地基,无论方案怎么变都不亏
3. 常驻机环境先用半天做**兼容性预检**(Python 3.14 下 FastAPI/NiceGUI/pydantic 可用性),据此定服务 Python 版本,再动工
4. flet 桌面 GUI 保持现状不迁移;等远控服务稳定后,再评估让 GUI 也走 API(方案 D 的 flet apk 同理,远期观察)
