# 「打开后无法退出 / 界面卡死」定位与修复 — 2026-09-10

> 触发：用户报告当前程序打开后**无法退出、界面卡死**。
> 排查对象：另一个会话在 v2.4.3～v2.4.6 引入的「远控开关 + 关闭按钮最小化到托盘/退出选择」。
> 结论：**`prevent_close=True` 与 `os._exit(0)` 组合使用，导致 flet 桌面客户端进程被遗留成孤儿窗口**。

---

## 一、结论（先看这个）

程序退出走的是 `os._exit(0)`（`源码/gui_app.py` 的 `_彻底退出`），而窗口被
`page.window.prevent_close = True` 拦截、不走原生关闭。

flet 桌面是**双进程**架构：Python 侧是 Flet 协议服务端，Flutter 客户端 `flet.exe` 是独立子进程。
`flet/app.py:308-320` 的正常收尾顺序是：

```python
fvp, pid_file = await open_flet_view_async(...)   # 拉起 flet.exe 客户端
with contextlib.suppress(Exception):
    await fvp.wait()                              # 等客户端进程退出
close_flet_view(pid_file)                         # os.kill(pid, SIGKILL) + 删 pid 文件
```

`os._exit(0)` **不展开调用栈、不跑 finally/atexit**，所以 `close_flet_view()` 永远不执行
→ `flet.exe` 成为**孤儿窗口**：界面还在、后端已死、点关闭没反应。
这就是"无法退出 + 界面卡死"的直接原因。

**引入点**：`0abdd09`（feat(gui): 远控开关 + 关闭按钮最小化到托盘/退出选择）。
`2b75229` 加的"关闭处理异常时直接退出"保险阀只处理了"异常路径"，没有触及这个
架构层问题——因为异常路径没错，错的是**唯一出口本身就是错的**。

## 二、证据链

### 2.1 源码证据

| 证据 | 位置 | 说明 |
|---|---|---|
| `prevent_close = True` 拦截原生关闭 | `源码/gui_app.py`（`page.window.prevent_close = True`） | 关闭按钮不再终止窗口，只能靠代码关 |
| 退出唯一出口是硬杀 | `源码/gui_app.py` `_彻底退出()` → `os._exit(0)` | 跳过 flet 收尾 |
| flet 的收尾依赖 `fvp.wait()` 返回 | `flet/app.py:308-320` | `os._exit` 后这段代码永不执行 |
| 客户端进程由 pid 文件被 SIGKILL 回收 | `flet_desktop/__init__.py:313-335` `close_flet_view()` | 该函数是唯一的客户端回收点 |
| 客户端是独立进程 | `flet_desktop/__init__.py:286/308` `subprocess.Popen` / `create_subprocess_exec` | 佐证"双进程" |
| 真正的关闭 API 存在但从未被调用 | `flet/controls/core/window.py:355/367` `destroy()`/`close()` | `destroy()` 才是终止入口 |

### 2.2 最小复现实验（决定性）

用 `.workbuddy/cache/退出复现.py`（同一份最小 Flet 应用，`prevent_close=True`，
6 秒后按指定方式退出），每种方式各跑一遍，统计 `flet.exe` 残留：

| 退出方式 | Python 进程 | `flet.exe` 客户端 | 判定 |
|---|---|---|---|
| `os._exit(0)`（**旧实现**） | 退出 | **残留孤儿**（实测 PID 53324 存留） | ❌ 死窗口、关不掉 |
| `await page.window.destroy()` 单独 | **永久挂住**（`ft.run()` 不返回，22s 仍在） | 正常回收 | ❌ 进程不退 |
| `destroy` + 等 1.5s + `os._exit(0)` | 退出（码 0） | 无残留 | ✅ **正确** |

第三种也解释了为什么"单纯改成 destroy 就完事"是不成立的：flet 在 destroy 后事件循环不返回，
必须补一次收尾强退。

### 2.3 次要卡顿（同类"卡死"体感，独立成因）

`_切远控` 是**同步**回调，内部 `import time; time.sleep(0.5)` —— 直接睡在 Flet UI 线程上，
这 0.5 秒窗口不响应任何事件（点什么都没反应）。已改为 `page.run_task` + `await asyncio.sleep(0.5)`。

## 三、修复方案

### 3.1 新增：`源码/gui_components/退出流程.py`（可单测）

把退出固化为**唯一出口**，顺序不可改，且每一步失败都不阻断后续（退出必须能完成）：

| 步 | 动作 | 为什么 |
|---|---|---|
| 1 | 停内嵌远控（非阻塞，只置 `should_exit`） | 不阻塞退出 |
| 2 | 停托盘图标 | 否则托盘残留 |
| 3 | 置位运行中任务的 `stop_flag`，等 ≤3s | 让爬虫写完检查点（保住断点续传） |
| 4 | 收尾钩子：爬取历史/站点历史/风控事件 flush + 日志 close | **第 7 步不跑 atexit**，不显式落盘就丢数据 |
| 5 | `await page.window.destroy()` | **回收 flet.exe 客户端进程（本次修复的核心）** |
| 6 | `await asyncio.sleep(1.5)` | 给 `fvp.wait()` → `close_flet_view()` 留时间 |
| 7 | `os._exit(退出码)` 兜底 | `ft.run()` 不返回，必须强退；此时客户端已回收，不再是孤儿 |

设计上把 `休眠` / `强制结束` / `记录` 做成可注入参数，因此整条退出路径**可以在单测里完整跑通**。

### 3.2 接线：`源码/gui_app.py`

- `_彻底退出()` 改为薄封装，调用 `执行退出(...)`，传入托盘对象、停远控、TaskManager、收尾钩子
- `_收尾落盘()` 显式 flush 爬取历史 / 站点历史 / 风控事件，并关闭日志句柄
- `_显示主窗()` 补 `page.update()`（原先改完可见性不刷新）
- `_切远控` 拆为「同步调度 + 异步执行」，消除 UI 线程上的 `time.sleep(0.5)`

### 3.3 新增单测：`测试/test_exit_flow.py`（14 例）

覆盖：**顺序**（destroy 必须先于强制结束、收尾钩子先于 destroy）、前序步骤（停远控/停托盘/
stop_flag/等检查点）、**容错**（destroy 抛错、钩子抛错、任务表抛错、停远控抛错、日志句柄已关，
五种情况下都必须仍然退得掉）。

**过程插曲（说明门禁确实有效）**：把 `_切远控` 改成异步时，静态检查立刻报出
`源码/gui_app.py: block=_切远控异步 未定义引用 -> asyncio` —— 本文件惯例是在函数内局部
`import asyncio`，我漏了。若无这道门禁，打包出的 EXE 点远控开关会静默失效（异常被外层
`except` 吞掉）。已修。

## 五、标准升级/发版流程（已固化并执行）

新增 `脚本/发布流程.py`：**门禁化流水线，任一步失败立即中止，不进入下一步**。

```
① 离线回归   python -m unittest discover -s 测试          必须 OK
② 手写回归   python 测试/回归测试_修复验证.py              必须 "0 失败"
③ 静态检查   python 脚本/check_undefined_refs.py           必须 "全部干净"
④ 打包 EXE   python 脚本/build_exe.py [--bump=...]         必须产出 dist/*.exe
⑤ 冒烟       build_exe.py 内置(启动 EXE 验活)，失败即构建失败
⑥ 提交       git add -A && git commit                     需工作区干净进入
⑦ 推送       git push origin main                         剥掉代理环境变量后推送
```

关键约定（都是踩过的坑）：
- **门禁前置于打包**：打包一次数分钟、还会消耗版本号并改写 CHANGELOG，门禁不过就打包等于白烧
- **推送前剥代理**：环境注入的 `http(s)_proxy` 对大连接不稳（挂起/502），`脚本/发布流程.py` 已内置
- **无产物即失败**：打包命令报成功但 `dist/` 无 `.exe`，判为失败（防"静默降级"）

用法：

```bash
python 脚本/发布流程.py --仅门禁        # 只跑 ①②③
python 脚本/发布流程.py                 # 门禁 + 打包 (不提交不推送)
python 脚本/发布流程.py --push          # 全流程
```

## 六、遗留（未在本轮处理）

- `flet.exe` 的孤儿进程若已存在，需用户手动结束（沙箱内 `taskkill` 被拦截，我无法代为清理）。
  修复上线后不再产生新的孤儿。
- `page.window.close()` 在本版本配合 `prevent_close=True` 会被再次拦截并回报 CLOSE 事件
  （`window.py:367` 文档明确），因此**不可**用它做退出；已统一走 `destroy()`。
- 远控开关的"端口被占"判定仍靠 `await asyncio.sleep(0.5)` 的经验值，理想做法是轮询
  `运行中()` 直到超时；本轮只消除了阻塞 UI 的问题，未改判定逻辑（避免扩大改动面）。
