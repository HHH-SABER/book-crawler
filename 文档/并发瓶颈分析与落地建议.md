# 并发瓶颈分析与落地建议

> 日期：2026-09-08
> 范围：`源码/` 下的章节抓取并发路径（章级 + 书级）
> 依据：代码静态分析 + `rust_core_poc/` 真实样本 A/B 实测（Python 3.14.1 / 8 线程）

---

## 一、当前并发架构

**两层线程池并发：**
- **章级并发**：`爬虫.py` 用 `ThreadPoolExecutor(max_workers=threads)` 并行抓取各章（线程数由 `速度自适应` 自动升降档，默认 1~6，或 `--threads` 手动）。
- **书级并发**：批量多本书并行（按设备核数推导 2~3 本），每域名用信号量限制 1 个并发任务。

**单 worker 的每章链路**（`_fetch_chapter_worker` → `_fetch_with_qc` → `get_chapter_content`）：

```
网络请求 session.get   →   HTML解析(lxml)   →   正文解码   →   清洗 clean_content   →   语义质检
  (等待时释放GIL)        (C解析释放GIL)       (纯Python持GIL)  (纯Python正则持GIL)     (纯Python持GIL)
```

**并发正确性已处理好的部分（不是瓶颈）：**
- Session 线程本地隔离（`threading.local`）、driver 每线程独立实例 —— 无共享竞态。
- `内容质检器` / `content_decoder` / `sites_config` 提取均无状态、线程安全。
- `爬取历史` 已做"5s 防抖 + 脏标记"（M1 优化），非每请求全量写盘。

## 二、瓶颈清单（按影响排序）

### 🥇 瓶颈 1：纯 Python 的 CPU 计算持有 GIL，把所有并发 worker 串行化

网络等待和 lxml 的 C 解析会释放 GIL，所以多线程在"等 HTTP"时确实并行；**但一进入正文解码 / 清洗 / 质检这些逐字符 + 多正则的纯 Python 步骤，就只剩 1 个线程在算，其余 worker 全部排队**。这三个步骤都无共享状态、可并发，纯粹被 GIL 卡死：

| 步骤 | 位置 | 性质 |
|---|---|---|
| 码点流解码 | `content_decoder.py → parse_codepoint_stream` | 逐字符状态机 |
| 语义质检 | `内容质检器.py → 质检()` | CJK/乱码/标点统计 + 正则 |
| 正文清洗 | `爬虫.py → clean_content`（含拼音/广告/零宽字符多正则） | 纯 Python 正则链 |

书级并发同样受这一个**进程级 GIL** 约束——所有书、所有线程的 CPU 步骤最终都在抢同一把锁。

**实测依据（真实样本）**：8 线程并发下，仅"解码 + 质检"两者：

| 实现 | 质检吞吐 | 相对 Python 线程 |
|---|---|---|
| Python 线程 | ~1,100 /s | 1x |
| Rust 持 GIL | ~12,000 /s | ~11x |
| Rust 释放 GIL | ~43,000 /s | **~39x** |

持 GIL vs 释放 GIL 之间差 **3.5~4.8x**，这就是 `py.allow_threads` 让多核真正并行的纯收益；叠加 Rust 本身约 11~13x 单核加速，叠乘后收益显著。

### 🥈 瓶颈 2：`站点历史` 每次任务全量序列化写盘

`站点历史.py` 在 `_io_lock` 下"改字典 + 写 .tmp + os.replace"，**未做防抖**——和 `爬取历史`（已防抖）不一致，属于漏网的写盘串行点。只在任务收尾调用，频率低，影响中等偏小。

### 🥉 非瓶颈 / 建议不动

- `请求引擎._requests_lock`：仅在反爬机制命中走引擎路径时触发，正常流程不经过，且请求 IO 本身释放 GIL —— 影响小，不动。
- 局部 `_resp_cache_lock`：短临界区，保护缓存读写的必要锁，收益远大于开销。

## 三、落地建议

### P1 —— 把"解码 + 质检 + 清洗"接进 Rust 扩展（收益最大）

已完成 PyO3 改造的 POC：`rust_core_poc/pyo3_ext`（abi3，可编译成 `rust_core.pyd`，已实测 3.12~3.14 兼容加载，含 `_gil`/`_nogil` 双入口）。落地时：

1. **改造 `内容质检器.py`**：顶部条件导入 + 全局兜底
   ```python
   try:
       from rust_core import qa_质检_nogil as _rs_质检
       _RUST_OK = True
   except (ImportError, OSError):
       _RUST_OK = False
   ```
   `质检()` 内加分支：`_RUST_OK` 时用 Rust 返回的 `(得分, 有效, 原因)` 构造 `质检报告`；否则走原 Python 实现。报告所需的统计字段由 Rust 一并返回或按需重建。

2. **改造 `content_decoder.py`**：函数签名完全一致，直接替换函数体为：
   ```python
   def parse_codepoint_stream(content, replace_map=None):
       if _RUST_OK:
           return rust_core.parse_codepoint_stream_nogil(content, replace_map)
       return _原实现(content, replace_map)
   ```

3. **`clean_content`**：正则较多，交由下轮评估是否同样移植（收益占比取决于正文清洗耗时）。

**要点（低风险、可回滚）**：Rust 实现必须 **逐字节/逐项与 Python 输出一致**（POC 已用真实样本 + token 级 + 8 组边界样本验证全部 PASS）。`.pyd` 缺失时 `ImportError` 自动回退 Python 实现，**不破坏现有 EXE 分发**，属于"有则提速、无则照旧"。

### P2 —— `站点历史` 写入加防抖（小改动）

照抄 `爬取历史.py` 的 M1 模式：加 `_上次落盘` + `_脏`，非强制时若距上次落盘 <5s 只标脏，任务收尾/`atexit` 强制刷盘 + 原子替换。可直接消掉书级并发收尾时的写盘串行。

### P3 —— 打包集成（PyInstaller）

将 `rust_core.pyd` 纳入 `小说爬虫.spec` 的 `datas`/`binaries`。注意 abi3 产物支持 3.12~3.14，但**仍依赖 Python 运行时**——本方案不会提供"免 Python 单二进制"的能力（那是另一个架构）。

---

## 四、风险与边界

- **正则语义差异**：若后续移植含向后断言/命名分组的模块（如 `反爬检测器`），需用 `fancy-regex` 或保留 Python 兜底；本批三个函数均为字节/字符级运算，无此问题。
- **并发安全**：Rust 函数无共享状态 + `allow_threads` 释放 GIL，与现有线程池正交，无新增锁。
- **多平台**：当前只验证了 Windows-msvc（Termux/安卓需交叉编译，暂不在本期范围）。

---

## 五、预期收益

- **单核**：解码 ~13x、质检 ~11x。
- **多核并发**：解码 + 质检从"进程内 1 核轮流算"变成"多核并行"，章级/书级并发的 CPU 吞吐对这两步可提升 3~5x（叠加单核加速，整体数十倍于纯 Python 并发）。
- 端到端占比取决于"CPU vs 网络"开销比：对 32KB 强解码大章、或本地/高速网络场景提升最明显。
