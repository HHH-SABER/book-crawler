## 一、跨平台检索可行性对比 (第一手反爬观察)

| 平台 | 检索通道 | 实际结果 | 反爬观察 |
|---|---|---|---|
| GitHub | Search API (未授权 10req/min) | ✅ 顺畅, 命中 5 个同类项目 | 限流但可预期, 生态绝对主场 |
| **Gitee** | v5 搜索 API / 网页搜索 | ❌ **API 未授权返回空 `[]`; 网页搜索弹百度安全验证码(滑块)** | **平台自身即重度反爬实践者**: 未授权 API 静默空响应 + 人机验证, 自动化检索被双通道阻断 |
| GitLab | v4 API (公开, `simple=true`) | ✅ 顺畅, 命中 Shosetsu 等 | 最开放; 但中文网文爬虫生态薄弱 |
| Bitbucket | 仓库搜索 API | ❌ **官方已废弃** (CHANGE-2770) | 平台重心在企业私有仓, 开源发现能力已放弃 |

**平台级结论**: 同类项目的"主场"在 GitHub (星标经济 + 搜索开放); Gitee 上即使存在
同类项目, 也对自动化检索不友好 (与本项目要对抗的站点行为同构); GitLab 生态偏
"国际应用" (如 Shosetsu 安卓阅读器); Bitbucket 可忽略。**跨平台可借鉴的实质增量
来自 GitLab 的 Shosetsu 与 Gitee 的平台行为本身**。

## 三、技术流派归纳 (四条路线)

### 流派 A: 规则外置 + 社区分工 (owllook / Shosetsu)
- **思路**: "站点多变"是永恒问题 → 把站点适配做成**可扩展资产**, 让社区分工维护。
  - owllook: 规则文档化 + 200+ 站声明式解析
  - Shosetsu: **Lua 可执行脚本源**, 用户/社区各写各的源, App 只做引擎; 源可热更新
- **优点**: 单站失效只影响一个源, 修复不依赖作者; 覆盖面随社区指数增长
- **缺点**: 脚本质量参差; 引擎要为"任意脚本"做沙箱/兼容 (Shosetsu 为此维护完整
  Lua 绑定); 对闭源单人项目是重资产
- **对应流派**: 本项目 sites_config (Python 内配置) 是"半外置"; 已具备插件式解码链

### 流派 B: 换数据端点, 绕开网页反爬 (jjwxc)
- **思路**: 网页端反爬最重 (验证码/指纹/渲染) → **不打网页, 直接走 APP 接口源**
  (jjwxc 的 app源/接口、本项目 datafile 模式同类)。接口端反爬通常只有签名+频率。
- **优点**: 避开整个浏览器伪装/验证码栈; 稳定性高、速度快
- **缺点**: 接口需要逆向(签名/加密参数), 且接口变更比网页更突然; 有明确 ToS 风险
- **本项目映射**: datafile/ajax 模式 + `_get_with_js_challenge` 已是此思路;
  jjwxc 的增量点是 **把 APP 源当"首选源"而非回退源** (接口优先, 网页兜底)

### 流派 C: 重客户端伪装 (本项目)
- 三引擎降级 + TLS 指纹 + 代理池 + 验证码五策略 —— 在跨平台样本中**最完整**。
- 代价: 打包体积 (Playwright/chromium)、维护面、单机定位。

### 流派 D: 发布工程化 (POf-L)
- 反爬之外的"可用性护城河": CI 构建 + 自动更新 + 签名双通道。
- 用户流失往往不是"爬不到", 而是"更新后坏了/不会装"。

## 四、跨平台项目技术选型对比结论

| 对比轴 | GitHub 主流 | GitLab | Gitee | 本项目 |
|---|---|---|---|---|
| 并发模型 | requests 同步为主 (少数 aiohttp) | — | — | requests+curl_cffi+cloudscraper 三引擎 |
| 反爬重心 | 数据混淆破解 + 增量 + 登录态 | 引擎/源分离 | (生态封闭) | **全栈覆盖最全** |
| 规则组织 | Python 内配置 / 文档化规则 | Lua 脚本 | — | Python 配置 + 分发器 (半外置) |
| 分发 | Release/EXE | F-Droid/Release | — | 本地 EXE (无 Release 流水线) |
| 验证码应对 | 多数回避 (换端点) | 源内自持 | — | 主动对抗 (五策略) |
| 增量/状态 | record.json / 历史文件 | 源内 | — | 爬取历史 + 增量 + 域冷却持久化 |

**核心差异**: GitHub 项目的反爬 = "单点技巧" (字体表/APP源/UA); 本项目 = "体系化
治理" (引擎+代理+验证码+解码+监控)。跨平台检索中**没有发现比本项目更完整的单机
反爬栈**; 各家的独门点集中在"规则组织方式"与"换端点策略"上。

## 五、对本项目的增量启示 (在既有 P0-P2 之外)

| 建议 | 来源 | 取舍理由 |
|---|---|---|
| **接口源优先策略**: 接口/数据文件当首选源, 网页当兜底 | jjwxc (APP 源) | 现有 datafile 模式已具备; 只需在 run_crawl 源探测顺序上"接口优先" — 低成本 |
| **源规则"可执行化"的远期形态**: 若未来源数量 >30 且有社区, 评估 Lua/JS 沙箱源 (Shosetsu 模式) | Shosetsu | 当前 8-9 站规模 **不做** — 收益不抵沙箱/绑定维护成本; JSON 规则化 (已列 P2) 是当前正确档位 |
| **延时设置暴露给用户** (config 可调, 带默认安全值) | ying-ck | GUI 已有速度自适应, 可加"站点级延时覆写"进站点编辑卡 — 低成本 |
| **网络代理坑文档化** (系统代理导致 ProxyError 的 Q&A) | ying-ck | 本项目已 trust_env=False 直连规避 — 已覆盖, 无需动作 |
| **F-Droid 式"可验证发布"意识** | Shosetsu | 归入 GitHub Actions Release (P1 已列), Release 附 hash 即可 |

自研 ruia 式框架; Lua 沙箱 (规模未到)。

## 六、结论

1. **平台层面**: 中文网文爬虫的开源主战场在 GitHub; Gitee 对自动化检索不友好
   (API 空响应+验证码, 其本身是反爬样板), GitLab 只有国际向阅读器生态,
   Bitbucket 已放弃代码搜索 —— **跨平台扩展检索的实质增量有限, 但平台行为本身
   验证了本项目反爬栈的必要性**。
2. **技术层面**: 各项目反爬 = 单点技巧 (字体表/换端点/UA); 本项目 = 全栈体系
   (已覆盖六维度中的五维半), 在单机反爬完整度上处于同类顶部。
3. **最值得吸收的三点**: ①接口源优先 (jjwxc) ②站点级延时/配置暴露 (ying-ck)
   ③可验证发布 (Shosetsu/POf-L) — 三者都是低成本高确定性增量。
