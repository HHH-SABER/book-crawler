## 二、逐项目深度分析

### 1. owllook — 多站点规则的"极致外置"
- **架构**: Web 服务 (Sanic) + 异步抓取 (aiohttp) + Mongo 存业务数据 + Redis 缓存; 自研轻量
  爬虫框架 `ruia`; 衍生生态 (owllook_api / owllook_gui / NIYT 终端版) = **API 与 UI 分离**。
- **关键实现**: 站点解析规则**声明式 + 文档化** (`docs/规则定义.md`), 已覆盖 200+ 站点,
  用户可自行添加解析 —— 这正是"多站点适配"的规模化答案。
- **依赖选型思路**: 重 (Mongo/Redis/Sanic) 但与其"在线服务+用户体系+推荐"目标匹配。
- ⚠️ 已停更 2 年, 且作者声明"不维护"。

### 2. ying-ck/fanqienovel-downloader — 单机工具的功能完备度样本
- **架构**: 单站点, 但**产品形态三端覆盖** (CLI 菜单 / Web 队列服务 / Termux 手机);
  `config.json` 外置可调 (段首占位符、延时、存储位置、保存模式), `record.json` 记录已下载
  id → **天然增量更新**。
- **关键实现**: 队列批量下载、在线阅读、Docker 数据卷持久化; 作者还做了**衍生工具生态**
  (c.exe 检测站点结构变化 / 搜索器 / 文件分割器)。
- **依赖选型思路**: 极轻 (requests+bs4+tqdm+ebooklib), 符合"单机小工具"定位。
- AGPL-3.0 + 完整免责声明 (合规意识值得学)。

### 3. POf-L/Fanqie-novel-Downloader — 发布工程化的天花板
- **架构**: main 分支**已无应用源码**, 只剩 `.github/workflows` (build-release.yml 116KB)、
  `scripts/` (发布/签名/更新元数据/发布说明生成)、`tests/` (测的是发布脚本本身)。
- **关键实现**: CI 构建多平台产物、签名/未签名双发布通道、updater 元数据规范化、Release
  资产审计、Issue 模板门禁 —— **把"打包分发"当成一等公民工程**。
- 启发: 一个工具的口碑, 一半来自"用户拿到手能否顺利安装更新"。

### 4. jjwxcNovelCrawler — 反爬对抗 + 结构熵增的双向样本
- **目录**: `client.py` + `TXT下载/` + `epub下载/` + `exe整合版/` + `反爬虫对照表/字体处理.py`
- **值得看**: `反爬虫对照表` + 字体处理 = **自定义字体(woff)反爬**的对照表破解方案,
  这是本项目目前**未覆盖**的反爬类型。
- **不该学**: 三套平行目录 + 大量 "(旧版备份).py" 混在正式目录、EPUB2/EPUB3 各复制一份 ——
  典型"靠复制目录做功能分支"的熵增结构。

### 5. lightnovel_epub — 导出管线 (未经逐行核实, 仅据 README 描述)
轻之国度/轻小说文库 → EPUB 生成。对本项目价值集中在**导出格式**: 本项目仅输出 TXT,
EPUB 有元数据/目录/封面, 阅读体验与分发价值明显更高。

## 三、借鉴清单

### ✅ 值得直接借鉴

| 做法 | 来源 | 本项目落地建议 | 收益/成本 |
|---|---|---|---|
| **EPUB 导出** | ying-ck / lightnovel_epub | 加 `ebooklib`, TXT 之外可选导出 EPUB (章节=chapter, 书名=metadata) | 高/中 (需新依赖, 打包体积略增) |
| **站点规则外置为数据** | owllook | 纯选择器型站点抽成 JSON/YAML 规则; 复杂站 (qsbs/datafile/分卷) 仍留代码适配 | 高/中 (接站成本↓, 社区可贡献) |
| **GitHub Actions 自动构建 Release** | POf-L | 加 workflow: push tag → 打包 → 上传 EXE 为 Release 资产 | 高/中 (免去手动分发 322MB) |
| **增量更新 (已下载 id 记录)** | ying-ck | 本项目已有爬取历史+增量开关, 可对标再加"一键更新书架"入口 | 中/低 |
| **合规声明与许可** | ying-ck (AGPL+免责) / owllook (Apache) | README 补"仅供学习、24h 内删除、不商用"声明 | 高/低 |
| **API 与 UI 分离** | owllook (owllook_api) | 保持 `run_crawl` 可独立调用 (已具备), GUI 只做编排 | 中/低 (已满足) |
| **字体反爬对照表 (储备)** | jjwxc | 遇 woff 字体混淆站时按"对照表"模式扩展解码器 | 中/中 (当前未遇到) |

### ❌ 不适合借鉴 (及原因)

| 做法 | 来源 | 不采纳原因 |
|---|---|---|
| Mongo + Redis + Sanic 服务化架构 | owllook | 本项目是**单机桌面工具**, 引入数据库/服务层是数量级复杂度, 无收益 |
| Web 版 (server.py + 浏览器 UI) | ying-ck | 已有 flet 桌面 GUI, 再上 Web 是重复投入且要维护两套 UI |
| 多目录并行复制 (TXT下载/epub下载/exe整合版) | jjwxc | 熵增结构, 三份重复实现难同步; 本项目已用配置+分发器统一, 更优 |
| 重度发布流水线 (116KB workflow、签名双通道、Issue 门禁) | POf-L | 单人项目过度工程; 只取其"自动构建 Release"这一层 |
| 引入 Scrapy 等框架 | (通用建议) | 桌面 GUI 单机场景用不上其异步管道/去重/中间件, 反而增加打包体积与复杂度 |
| 自研爬虫框架 | owllook/ruia | 本项目已有 请求引擎三件套 + 反爬检测器, 自研框架无增量价值 |

## 四、针对本项目的改进建议 (按优先级)

| P | 建议 | 理由 | 取舍说明 |
|---|---|---|---|
| **P0** | **README 补合规声明** (仅供学习/勿商用/24h 删除) | 同类头部项目全部有; 零成本、规避风险 | 只写声明, 不改功能 |
| **P1** | **GitHub Actions 构建 Release** (tag 触发 → 打包 → 资产上传) | 解决 322MB EXE "不入库也没法分发"的尴尬, 用户可直接下载 | 用 GitHub Runner 免费额度; 本地手工打包保留为兜底 |
| **P1** | **EPUB 导出** (ebooklib) | 当前只有 TXT, 是功能面明显缺口; 同类项目标配 | 新增 ~1 依赖, 体积影响小; 做成**可选导出**不影响 TXT 主流程 |
| **P2** | **站点规则数据化** (选择器型站点 → JSON 规则文件) | 对齐 owllook 的规模化思路, 降低新站接入门槛 | 复杂站仍用代码适配, 不做"全部配置化"的过度抽象 |
| **P2** | **"一键更新已抓书籍"入口** | 对标 ying-ck record.json; 本项目已有增量能力但入口不明显 | 复用现有爬取历史, 低成本 |
| **P3** | **字体反爬解码器储备** | 应对未来遇 woff 字体混淆站点 | 当前 8 站未遇到, 不提前实现, 保持解码器链可扩展即可 |

**不做的明确取舍**: 服务化/Web 化/自研框架/重型依赖 —— 保持"单机桌面工具"定位带来的
轻量、零部署、数据留在本地三大优势; 本项目真正的护城河是**多站适配深度 + 混淆解码 +
反爬治理**, 应把资源投在这三项与"导出/分发体验"上。
