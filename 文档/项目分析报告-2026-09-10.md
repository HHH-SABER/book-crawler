### 2.2 最关键的一条架构事实：**GUI 状态靠正则解析日志文本推进**

爬虫已经不 print 了（改为 `日志.py` 的统一 logger），但 `日志.py:134` 保留了 console 镜像 print，
`task_manager.py:269-356` 的 `_ThreadAwareStdout` 用**线程 ID + contextvar** 把输出分发回对应任务，
再由 `task_manager.py:86-213` 用 **14 条正则**把文本翻译成 `status / title / progress`。

这是整个项目最脆的地方：**改一条日志文案就可能静默打断界面状态机**。虽然 `test_log_contract.py`
已经为这条通道补了契约测试（这是前一轮做对的事），但它仍然意味着"日志文案"事实上是公开协议，
却长得像普通日志。这是我认为**下一个大版本最值得动的结构性项**，优先级高于拆分 `爬虫.py`。

### 2.3 站点适配三层的真实优先级

`sites_config.get_site_pattern()` → 先 `_apply_runtime_config()`（JSON 按域 upsert 覆盖内置），
再 `load_adapters()`（插件 upsert）。所以实际优先级是：

**插件 > `站点配置.json` > 内置 `SITE_PATTERNS`**

两个坑：`reload_runtime_config` 只重放 JSON 层（插件层不动）；重放时会**剥离所有条目的 `enabled`**
（`sites_config.py:441`），这正是 H4 的机制来源。

### 2.4 线程模型（[子分析] + 抽查）

- Flet 主线程只做控件树与 `page.update()`；刷新靠两个 `page.run_task` 异步循环（各 1s）
- 每任务一条 daemon 线程；站点探测一条；pystray 一条；uvicorn 一条
- 回传以**轮询 + 锁**为主，仅托盘回调与站点探测用 `page.run_task`
- 未发现 worker 直接碰 Flet 控件——这条规约**执行得不错**
- 唯一阻塞事件循环的地方：`gui_app.py:351` 的 `time.sleep(0.5)`

## 三、本轮新发现

### 高

**N1 · CI 里的 Rust 编译永远静默失败，发布产物永远是纯 Python [实测]**

`.github/workflows/release.yml:53`：

```bash
(cd rust_core_poc/pyo3_ext && ../.venv/Scripts/python.exe -m maturin build --release) \
  || { echo "[WARN] rust_core 编译失败, 本次发布为纯 Python"; exit 0; }
```

从 `rust_core_poc/pyo3_ext` 出发，`../.venv` 解析为 `rust_core_poc/.venv`。
**实测该路径不存在**（仓库 venv 在根目录，`rust_core_poc/` 下没有 `.venv`），
所以这行必然失败，被 `|| { ... exit 0; }` 吞掉，步骤仍报绿。

后果：`源码/rust_core.pyd` 虽然本地存在（我确认了），但**从不入库**，因此
**每一次 CI 发布出来的 EXE 都没有 Rust 加速**，且只有日志里一行 WARN。

这直接推翻前一轮修复台账里 **M12「release 现场编译 rust_core.pyd ✅」** 的结论——
动作写了，路径错了，等价于没修。修法：`../.venv` → `../../.venv`（且最好把失败改为显式警告注记）。

**N2 · 全项目 163 处 `except ...: pass`，其中 143 处是 `except Exception` [实测]**

项目自己的规约写着"裸 except 必须留痕"，AGENTS.md 也明确禁止 `except Exception: pass`。
实测分布（按文件）：

```
20  gui_components/pages/site_manage_page.py
18  gui_app.py
13  爬虫.py
11  gui_components/task_manager.py
 8  captcha_module.py / 日志.py / log_tab.py
 7  远控/服务.py
```

按异常类型：`Exception` 143、`OSError` 9、其余为组合元组。
**规约与实现之间已经裂开了一大截**——要么把规约改成现实（允许在明确无害处静默），
要么批量改成 `_log.debug(f'吞异常: {type(e).__name__}: {e}')`。我倾向后者，成本很低（可脚本化）。

**N3 · 速度自适应的"回升闸门"被自己清零，触底后单任务内不可回升 [实测]**

`速度自适应.py` 的回升判据在 `_maybe_upgrade_locked`（[:435-447]）：

```python
if self._risk_since_change > 0:   # :443 「期间无风险事件」
    return None
```

但 `_risk_since_change` 唯一的清零点在 `_change_tier_locked`（[:459]）——**每次换档都清零**。
于是：
- 风险事件**导致降档**时，计数被自己抹掉 → 该判据看不到任何风险事件；
- 在**最低档**再遇风险事件时（`note_risk` 走 [:401-403] 分支，不换档、计数不清零），
  计数永久 `> 0` → 该任务内**再也无法回升**。

影响面受限于控制器是**按任务构建**的（`速度画像.json` 只缓存硬件画像、TTL 7 天，不是档位状态），
所以是"单次长任务内触底不回升"，不会跨任务恶化。但仍与设计意图相反。

### 中

**N4 · 质检的"综合得分不足"是死分支（复核实锤）[实测]**

`内容质检器.py:146-148`：

```python
报告.有效 = (报告.得分 >= 阈值_及格总分 and not 报告.原因)
if not 报告.有效 and 报告.得分 >= 阈值_及格总分 and not 报告.原因:
    报告.原因.append('综合得分不足')     # 永远到不了
```

同段还有不一致的守卫写法：[:136] 带 `and not 报告.原因`，[:138-142] 不带——
说明这里是多次打补丁叠出来的。配合"任何一项子分归零就追加原因 → `有效=False`"的语义，
docstring 里"总分 ≥60 即有效"的说法与实现**不一致**（M9 的判断成立）。

**N5 · 已完成的任务可以被"停止"改写成已停止 [子分析]**

`task_manager.py:493-505` 的 `stop_task` 不校验当前状态。表格里选中一条 `completed`/`failed` 的任务
点"停止"，会被 `_set_terminal(..., "stopped")` 覆盖。远控 `服务.py:299` 复用了同一入口 →
**手机端看到的终态与实际不符**，并且会触发一次错误的终态推送。修法是入口加状态白名单。

**N6 · 托盘"退出"绕过优雅收尾 [子分析]**

`gui_app.py:412-423` 走 `os._exit(0)`，绕过了 `on_disconnect`（[:517-527]）里的 `stop_flag` 置位与
`app_log.close()`。运行中的任务会被硬杀、**不落检查点**，与 [:514-516] 注释承诺的优雅退出矛盾。
对一个主打"断点续传"的项目来说，这是实打实的数据体验损失。

**N7 · 托盘启动失败 → 无窗僵尸进程 [子分析]**

`gui_app.py:425-440` 先把窗口 `visible=False`，**再**建托盘；若 `启动托盘` 抛异常，只置
`minimized=True`，托盘入口不存在 → 用户既看不到窗口也点不到托盘，只能杀进程。顺序应该反过来。

**N8 · 远控开关的启停竞态 [子分析]**

`远控/服务.py:99-115`：`停止后台()` 立刻把 `_server/_server_thread` 置 None，而 `运行中()` 只看
线程 `is_alive()`。于是"关→立刻开"可能在新 Server 里抢同一端口失败；反之线程刚起、端口未绑定前
`运行中()` 已返回 True，开关会**假成功**。测试 `test_remote_service.py:336` 只能靠换端口规避，
恰好坐实了这点。

**N9 · token 经 URL query 外发第三方 [子分析]**

`远控/服务.py:449` 把 token 直接拼进阅读链接（`?k=...`）发给 Bark/ntfy；
`面板.html:245,249`、`阅读.html:51` 同样用 URL 带 token 并写入 localStorage。
推送服务商的日志、以及浏览器的 Referer，都可能带走 token。鉴权实现本身是对的
（`hmac.compare_digest`），问题在**凭据传播方式**。建议改 header 或一次性短票据。

### 低 / 结构性

- **N10 · 请求引擎降级链在连接级失败时不降级 [子分析]**：失败计数只在"拿到响应但非 2xx"时自增，
  引擎方法异常时返回 `None`（`请求引擎.py:230/251/271`）被跳过 → 超时/连接失败永远不触发
  `cloudscraper → curl_cffi` 切换。另外 `:218-226` 的 session 缓存 `get` 与建 Session 在锁外，
  并发同域会互相覆盖（丢 cookie 且旧句柄泄漏）；`close()` 全项目无调用方。
- **N11 · 跨进程状态整文件覆盖 [子分析]**：GUI 与远控是两个进程，各持内存副本写
  `爬取历史.json`（451KB）/`站点历史.json`，后写覆盖先写。这类丢更新在"桌面 + 手机同时用"的场景下会真实发生。
- **N12 · 测试脚本残留空 `__main__` 块 [实测]**：`测试/回归测试_修复验证.py:312-315` 打印了开场横幅却
  不调用任何用例，真正的入口在 `:356`。虽然当前**不影响执行**（前一块执行完会继续往下走），
  但属于明显的残留，容易误导后来者。
- **N13 · 死代码 [子分析]**：`task_table.py:67-68` 的 `on_delete_task`/`on_redownload` 从未被赋值
  （对应分支恒不执行）；`ui_fluent.py:249-267` 四个函数全项目无外部调用；
  `detail_drawer.close()`、`icon_rail.toggle_theme_icon()` 无有效调用方；
  `请求引擎._引擎顺序`、`代理池` 的 domain 分支、`风控事件._ENABLED` 均无接线。
- **N14 · FilePicker 未注册到 services [子分析]**：`gui_app.py:168`、`site_manage_page.py:236`
  只在页面上下文实例化 `ft.FilePicker()`，从未加入 `page.services`/`overlay`。
  Flet 0.86 下这可能让 `pick_files` 无响应——**建议实机点一次确认**（我没法验证 GUI 交互）。
