# 沟通用语手册 · 界面相关需求该怎么说

> 面向「小说爬虫」项目的界面类需求。用户阿雯常需向 AI / 协作者提出界面类需求，
> 用词不准会导致**工作量误判**（例：用「重构」形容改配色，对方会以为要动整个组件树）。
> 本文给出**可直接复制的说法**。

---

## 一、⚠️ 最重要的一个坑：「重构」有专业歧义

在软件工程里，**「重构」（refactoring）= 不改变外部行为，只优化内部结构**。

| 你以为的「重构」 | 实际的「重构」 |
|---|---|
| 「把界面重新设计一下」 | 「代码不动外部表现，内部实现优化」 |
| → 改视觉、改布局、改交互 | → 抽函数、合并重复、消除上帝对象 |
| → **需要重新做设计稿** | → **设计稿完全不动** |

**所以：「重新设计界面」不要用「重构」，用「重新设计 / 重做 / 改版」。**

| 你想做的事 | ❌ 别用 | ✅ 准确说法 |
|---|---|---|
| 从头重新设计界面 | 重构界面 | **界面重设计 / UI 重新设计 / 改版** |
| 改配色、字号、间距 | 重构样式 | **视觉改版 / 视觉规范调整 / 设计 token 梳理** |
| 改布局、加/删页面 | 重构页面 | **交互改版 / 信息架构调整** |
| 改代码结构但界面不变 | 重构 | ✅ **重构**（本义，没说错） |

---

## 二、按「你想做的事」选词（可直接复制）

### 1. 从零设计一套新界面
> 「做一套 **UI 设计方案** / **界面设计方案**」

专业细分工：
- **UI 设计**（Visual Design）—— 视觉层：配色、字体、间距、图标、组件外观
- **UX / 交互设计**（Interaction Design）—— 流程层：点击后发生什么、状态怎么流转
- **信息架构（IA, Information Architecture）** —— 结构层：页面怎么组织、导航怎么排

⚠️ **UI 设计 ≠ UX 设计**。前者是「长什么样」，后者是「怎么用」。
本项目的「死书三态处置」属 UX，「莫兰迪暖色系」属 UI。

### 2. 改现有界面（最常用）
> 「**改一下现有界面**」/「**调整界面**」/「**界面优化**」

按改动范围细分：
- **微调 / 打磨**（Polish）—— 几个像素、几处间距
- **视觉改版**（Visual Refresh）—— 换配色、换风格，但布局不动
- **交互改版**（Interaction Overhaul）—— 改流程、改布局、加功能入口
- **界面重设计**（Redesign）—— 大改，但保留功能
- **界面重做**（Rebuild）—— 推翻重 来，功能也可能变

### 3. 加一个新页面/新功能区
> 「**新增一个『死书清单』页面**」/「**在侧栏加一个入口**」

专业说法：**新增功能模块 / 信息架构扩展**。

### 4. 只是要一份「图」来看效果
> 「**出一版界面预览图**」/「**画个界面稿**」

本项目对应物：Ardot 画板 + `界面设计预览/index.html`。
专业说法：**设计稿 / 视觉稿 / UI mockup**。

## 三、这个项目该用的专属说法

主程序是 **Python + Flet 0.86**（Flutter 渲染的桌面应用），**不是 Web 前端**。
所以有几类常见词**不适用**：

| ❌ 不适用 | 原因 | ✅ 应该说 |
|---|---|---|
| 前端 / 前端架构 | 本项目无 package.json / Vite / React/Vue | **界面 / GUI / 客户端界面** |
| 组件库改造 | 用的 Flet 自带控件 | **界面控件 / 页面组件** |
| 响应式适配 | 桌面窗口固定尺寸，不做响应式 | **窗口尺寸适配 / 不同分辨率适配** |
| 路由配置 | 6 个页用侧栏切换，非前端路由 | **页面导航 / 侧栏导航** |
| 主题切换（暗色模式） | ✅ **这个能用**，项目真支持 | 主题切换 / 深浅色模式 |

**本项目最贴切的三个说法**：
1. **界面重设计**（大改时）
2. **界面微调 / 打磨**（小改时）
3. **设计稿 / 界面预览图**（只要图的时候）

## 四、最省事的表达模板

需求可以套这个句式，AI 立刻知道要做什么、要不要先给方案：

> **「我想【动词】界面，范围是【哪些页面/控件】，希望达到【效果】。
> 动手前先【给我方案 / 直接改】。」**

四个真实例子：

1. 「我想**重新设计**界面，范围是**侧栏和死书清单页**，希望**信息层级更清楚**。动手前先给我方案。」
2. 「我想**调整配色**，范围是**运行日志页**，希望**夜间模式不那么刺眼**。直接改。」
3. 「我想**加一个**『死书清单』**页面**，挂在**侧栏爬取历史后面**。先给我布局方案。」
4. 「**代码别动**，我只想先**看一版设计稿**。」

**第 4 条特别重要** —— 这正是上一轮做的事（只出设计稿、不改 `源码/`）。

---

## 五、给 AI 提界面需求的三个要点（经验总结）

1. **说清「改不改代码」**。只出稿就说「先别动源码」；要落地就说「改完跑测试 + 打包实测」。
2. **说清范围**。「界面」太笼统，明确到**哪几个页面 / 哪个控件**。
3. **说清依据来源**。本项目有铁律：**配色/尺寸/文案一律以真机为准**，不能凭旧设计稿猜。
   提需求时最好带上「**按实机真值**」这句，能省掉一轮返工。

---

> **一句话总结**：日常说「**改界面**」就够专业了；
> 想要精确表达规模时用「**微调 / 改版 / 重设计 / 重做**」四级区分；
> **永远别用「重构」来表达视觉层面的改动** —— 那是最容易造成工作量误判的词。
