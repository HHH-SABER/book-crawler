## 〇、核心判断（先说结论，不想读全文看这段就够）

**这个项目已经过了"加功能就有价值"的阶段，不该再去追 star、追功能。下一步的价值集中在三件事：**

1. **止血技术债**（内功）——上帝类、186 处静默吞异常、解密模块零单测。这些不解决，任何新功能都是在沙地上盖楼。
2. **精准借鉴一个能力**——站点适配「自愈」。这是项目维护成本最高、也最能形成壁垒的地方，开源里 Scrapling 已有成熟思路可学。
3. **想清楚产品定位**——守住「单机、离线、开箱即用、合规克制」这个身位，**不要**被 firecrawl/crawl4ai 的高 star 带偏，跑去和云端 AI 数据管道硬拼。那是不同赛道，拼不过也没必要拼。

**一句认知纠偏**：firecrawl 17.9 万 star 不代表它比这个项目"强"，只代表它踩中了 AI 风口、是给开发者调用的云端 API。它的成功路径和你这个桌面 EXE 工具完全不是一回事。**别用别人的 star 给自己制造焦虑。**

## 三、最值得深挖的两个同类项目

### Scrapling（80.6k，Python/BSD-3）— 和本项目最像，最该研究
- **自适应元素定位**：用元素的视觉特征+上下文关系做"指纹"，网站改版后能自动重定位到对应元素，而不是选择器一失效就抓空。
- 三层 Fetcher（HTTP / Stealth / Dynamic）统一接口 + 按域 AutoThrottle 自适应调速 + 内置反检测。
- **为什么对它最有价值**：本项目已经有「站点漂移 EMA 检测」，但**只告警不自愈**——检测到漂移后仍要人工去改 JSON 规则/插件。Scrapling 的思路正好补上"检测→自动尝试重定位"这后半段。这是把本项目从"能告警"升级到"能自愈"的关键一跳。

### MediaCrawler（64.9k，Python）— 多站点组织的范本
- 抽象基类定义平台统一接口（搜索/详情/评论），每平台一个子类，工厂模式按配置实例化。
- **为什么对它最有价值**：本项目站点适配是"JSON 规则 / 插件 / 内置正则"三层，但插件之间**没有强制的统一接口约束**，6 个适配器各写各的。学 MediaCrawler 定义一个 `BaseSiteAdapter` 抽象基类（目录解析/正文解析/反爬处理三个标准方法），能让新站点接入更规范、更好测。

## 四、这个项目的定位与护城河（升级前先认清自己）

**它是什么**：单机桌面、单文件 EXE、开箱即用、离线运行、合规克制的**个人小说阅读工具**。用户是普通人，不是开发者。

**护城河（已有、要守住、别丢）**：
- **五维语义质检**——绝大多数爬虫没有，这是"抓得干净"的核心保证
- **多引擎反爬降级**（requests→cloudscraper→curl_cffi）+ Playwright WAF——curl_cffi 已是当下最先进的 TLS 指纹方案之一，**反爬栈不需要大改**
- **站点适配积累**（6 插件 + 26 JSON 规则）——这是时间堆出来的资产
- Rust 加速、桌面 GUI + 手机远控、严格合规边界

**不该做的**：去和 firecrawl/crawl4ai 拼"云端规模化 AI 数据管道"。那是另一门生意（要服务器、要 API、要面对完全不同的合规风险），和本项目"单机离线个人工具"的基因冲突。

## 五、升级方向（三层，按优先级从高到低）

### 第一层 · 止血技术债（内功，优先级最高，先做这个）

> 不解决这些，第二三层都是空中楼阁。这些是前两轮实测确认的真实欠账。

1. **上帝类拆分**（`爬虫.py` 7,302 行 = 源码 32.6%）
   - 学 Scrapy 的**分层思想，但不引入 Scrapy**（太重，塞不进单机 EXE）。
   - 现实做法：按职责边界抽出 3 块最痛的——①解析层（目录/正文提取）②清洗质检层 ③断点存储层。每块独立模块、独立可测。
   - **不要追求一次拆完**，按"改动频率高 + 出错代价大"的块优先。

2. **186 处静默吞异常**（AST 实测，全项目 581 个 except 中 32%）
   - 违反 AGENTS.md 自己的规约（裸 except 必须留痕）。
   - 集中在 GUI 层：`gui_app.py` 23、`site_manage_page.py` 20、`task_manager.py` 16。
   - 危害：异常被吞后界面表现为"就是不动"，排障时无任何线索。
   - 做法：分批补 `_log.debug`，优先 GUI 层和 `task_manager.py`。

3. **零单测模块补齐**
   - `decrypt_utils.py`（6 种正文解密）和 `epub_exporter.py` 在测试目录**零引用**（实测）。
   - 解密错了不会报错，只会静默产出乱码→被质检拦成空占位，排查成本极高。
   - 用 `测试样本/` 已有的 HTML 快照做离线用例，补上解密 6 路径 + EPUB 导出。

4. **M2 非原子写**（`爬虫.py:5447` 检查点每章 `write_text` 直写）
   - 断电/进程被杀会留半截 JSON，而检查点是断点续传的命脉。
   - 项目里 `爬取历史.py` 就是 tmp+`os.replace` 的现成范式，照抄即可。

5. **依赖 lock**：`requirements.txt` 全 `>=` 无锁定，CI 又现场编译 Rust。上游跳版本可能让"今天能打的包明天打不出来"。补一份 lock（pip-tools / uv）。

### 第二层 · 精准能力升级（借鉴开源，守住定位）

1. **★最高价值：站点适配「自愈」**（学 Scrapling）
   - 现状：`站点漂移检测.py` 检测到漂移**只告警**，仍要人工改规则。
   - 升级：检测→自动尝试选择器重定位（元素指纹/上下文匹配）→成功则热更新规则、失败再告警。
   - 这是把维护成本最高的环节自动化，也是最能拉开和同类差距的能力。

2. **适配器抽象基类**（学 MediaCrawler 工厂模式）
   - 定义 `BaseSiteAdapter`（目录解析/正文解析/反爬处理三个标准方法），6 个插件逐步收敛到统一接口。
   - 收益：新站点接入更规范、可测性提升、为上面的"自愈"提供统一挂载点。

3. **LLM 提取兜底**（学 crawl4ai）— **可选，谨慎**
   - 思路：正则/CSS 提取失败时，降级用 LLM 提取正文/目录。
   - ⚠️ 冲突点：本项目是**离线单机 EXE**，引入 LLM = 要联网 + API key，与"离线"定位冲突，且要重新过合规审查。
   - 建议：只能作为**用户显式开启的"云端增强"选项**，绝不进默认路径，离线内核保持完整。优先级低于前两项。

### 第三层 · 产品定位（想清楚往哪走，再决定做什么）

- **主线**：继续做"最稳、最干净、最合规的个人离线小说阅读工具"。把第一层内功和第二层自愈做扎实，比加任何新功能都更能提升口碑。
- **AI 的态度**：作为**可选增强**（如 LLM 兜底提取、智能质检），不是主线。不要因为 crawl4ai/firecrawl 火就把整个产品转向 AI 数据管道。
- **规模化**：本项目天然不需要"分布式/海量并发"，单机克制反而是合规优势，别去补这个"短板"。
