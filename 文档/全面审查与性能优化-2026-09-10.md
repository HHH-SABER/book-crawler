## 一、本轮已落地的修复（5 项，全部过了回归门禁）

### ✅ 1. 任务列表排序崩溃（高危，静默瘫痪 GUI）

`源码/gui_components/task_manager.py` — `get_all_tasks()`

```python
key=lambda t: int(t.task_id.split('_')[-1])     # 旧
```

远控从 checkpoint 重建中断任务时写入的 task_id 是 `resume_<md5前8位>`
（`远控/服务.py:504`）→ `int('ab12cd34')` 抛 `ValueError` → 异常从 `get_all_tasks` 冒出，
被 GUI 刷新循环外层 `try` 吞掉 → **任务表、状态栏、远控页整体静默停摆，重启才恢复**。
触发条件很日常：手机上看到一个中断任务，桌面端就瘫了。

改法：新增 `_任务排序键` 静态方法，`(前缀, 是否数字后缀, 数值, 文本)` 四元组排序——
数字后缀仍按数值排（保住 M5 的 `task_2` 在 `task_10` 之前），非数字后缀退化为文本序，不再抛异常。

### ✅ 2. GUI 日志解析热路径（性能，实测 −95.5% 正则调用）

`源码/gui_components/task_manager.py` — `write()` / `_parse_progress()` / `_parse_metrics()`

`write()` 是**每条日志行**的唯一入口，而旧实现无条件跑 11 条正则（2 条在 write、
4 条在 `_parse_progress`、5 条在 `_parse_metrics`）。爬虫每章打印数十行 → 每章数百次必然失败的正则。

改法两条：
- **子串预判短路**：每条正则前加廉价子串判断。子串是正则匹配的**必要条件**，故语义完全等价。
  `_parse_metrics` 另加一次整体短路（`[反爬` 同时覆盖 `[反爬]` 与 `[反爬检测]`）。
- **原地截断**：`logs = logs[-500:]` 改为 `del logs[:-500]`。旧写法一旦超过 500 条，
  每来一行日志都要重建一个 500 元素的新列表。

**实测**（1000 行真实分布日志：70% 正文行 / 15% 进度行 / 10% 引擎行 / 3% 质检 / 2% 增量）：

| 指标 | 旧 | 新 |
|---|---|---|
| `re.search` 调用次数 | ~11,000 | **500**（−95.5%） |
| `write()` 总耗时 | — | 4.7 ms（4.7 μs/行） |

解析结果抽检正确：进度 `149/1000`、质检分 `92.0`、增量跳过 `20` 全部命中。

### ✅ 3. CPU 基准的锁是「一次性」的（正确性，且影响选档）

`源码/速度自适应.py:214`

```python
with threading.Lock():      # 旧: 每次调用新建一把锁 = 完全没有互斥
    total_hashed += local
```

新建的锁谁也拦不住谁 → 各线程累加丢更新 → 基准吞吐被低估 → 选档偏保守（抓得更慢）。
改法：模块级 `_BENCH_LOCK`。

### ✅ 4. 远控章节缓存并发淘汰（可致阅读页 500）

`源码/远控/服务.py` — `_解析章节()`

同步端点跑在 Starlette 线程池里，而 `len(_章节缓存) > 8` 与 `pop(next(iter(...)))` 之间无锁：
另一线程若把缓存清空，`next(iter({}))` 抛 `StopIteration`；迭代中被改则抛 `RuntimeError`。
两者都没被捕获 → 500。改法：新增 `_章节缓存锁`，读写与淘汰全部持锁，淘汰改 `while`。

### ✅ 5. 同一页被反复整页解码（性能，零风险）

`源码/爬虫.py:3906`

`response.text` 是属性、**无缓存**，每次访问都按推断编码重新解码整个 body。旧实现在 7 条
JSON 模式的循环里反复取 → 同一页最多整页解码 7 次。改法：循环外取一次。

## 三、性能结论：真正的墙钟瓶颈在网络等待，不在 CPU

### 3.1 最大的单项开销（未动，需灰度）

**`爬虫.py:4937-4938`：主 requests 路径每页硬编码 `time.sleep(random.uniform(0.5, 1.5))`。**

每页 1 次 × 1000 章 → **纯等待 500–1500 秒**；且与速度自适应的 `time.sleep(_cur_delay)` 叠加，
属双重延迟。这是整个项目最大的单项时间开销，但去掉会抬高封禁率——需要按站点灰度，
不适合直接改。建议做成「站点级开关 + 只有自适应未生效时兜底」。

### 3.2 已确认**不是**瓶颈（避免后人重复优化）

| 位置 | 结论 |
|---|---|
| `sites_config.py:396-406` | `get_site_pattern` 每次确实调 `_apply_runtime_config`/`load_adapters`，但都有幂等标志（`_RUNTIME_APPLIED`/`_ADAPTERS_LOADED`）→ **只首次读 JSON**，之后只是一次 `url.lower()` + 26 条线性子串匹配。**没有每章重读配置** |
| `爬取历史.py:138` | 最小落盘间隔 5s 防抖生效 → 千章真正 dumps ≈ 秒数/5，非千次 |
| `内容质检器._统计` | 同一文本被约 6 遍正则扫，但**有 `rust_core.pyd` 时走 Rust**，该函数不执行 |
| GUI 1s 循环 | `task_table.py:122` 有签名比对跳过重建、`detail_drawer.py:210` 有日志签名增量追加、`refresh()` 仅详情可见时运行 —— 已优化 |
| 并发闸门 | `速度自适应.py:371` 仅在 `_active >= threads` 时等待，池尺寸即档位，无额外串行 |
| `clean_content` | 约 65 次 `str.replace` + 逐行广告判定，单章 < 几 ms，低收益，不建议动 |

### ✅ 6. CI 的 Rust 编译路径 —— 前一轮台账 M12 的「已修」是假的

`.github/workflows/release.yml:53`

```bash
(cd rust_core_poc/pyo3_ext && ../.venv/Scripts/python.exe -m maturin build --release) \
  || { echo "[WARN] rust_core 编译失败, 本次发布为纯 Python"; exit 0; }
```

从 `rust_core_poc/pyo3_ext` 出发，`../.venv` 解析为 `rust_core_poc/.venv`（**实测不存在**），
命令必然失败且被 `|| { …exit 0; }` 静默吞掉 → 步骤报绿，而**每次 CI 发布的 EXE 都没有 Rust 加速**。
改 `../../.venv`，并在步骤内加注释说明为何必须是两级。

### ✅ 7. 托盘「退出」绕过优雅收尾

`源码/gui_app.py` — `_彻底退出()`

旧实现停掉远控与托盘后直接 `os._exit(0)`，绕过 `_on_disconnect` 的 stop_flag 置位与日志 flush
→ 运行中任务被硬杀、**不落检查点**，与本项目主打的断点续传直接矛盾。
现改为：先执行与 `on_disconnect` 相同的收尾（置位全部运行中任务的 stop_flag + flush 日志），
若确有运行中任务再 `await asyncio.sleep(3.0)` 让爬虫循环写完检查点，最后才 `os._exit(0)`（上限 3s 不挂住）。

### ✅ 8. 速度自适应回升闸门（同日报告 N3）

`源码/速度自适应.py`

删除 `_risk_since_change`（唯一清零点在 `_change_tier_locked`，换档即清零 → 判据自废；
在最低档遇风险时又只增不清 → 单任务内永久无法回升），改用时间判据：

```python
UPGRADE_RISK_FREE_SECONDS = 180   # 距上次反爬事件须静默这么久才允许回升
if time.time() - self._last_risk_time < UPGRADE_RISK_FREE_SECONDS:
    return None
```

**这是行为变化**：触底后只要「距上次反爬事件静默 180s + 连续 30 章成功 + 距上次换档 180s」
即可回升（旧行为是永久卡在最低档）。上界受站点档位上限 `_max_tier` 约束，不会越过站点配置。
同步更新了手写回归脚本的时序断言，并**新增 10 个单测**（弥补 M13 记录的「速度自适应降升档零覆盖」）。

### ✅ 9. 风控事件读路径竞态

`源码/风控事件.py`

`_LOCK` 由 `Lock` 改 `RLock`（写路径 `set_domain_cooldown` 会在持锁状态下回调读函数，
普通锁会自死锁）；`_load_state` 拆为持锁的 `_load_state` + `_load_state_locked`。
消除「读到 数据/mtime 错配组合 → 偶发错误冷却值」。

### ✅ 10. site_probe 既无 SSRF 校验、又泄漏连接

`源码/site_probe.py`

- 探测前过 `sites_config.validate_public_url`：非公网/非 http(s) 直接返回错误且**不发请求**
- 显式 `close()` 探测用的 Session 与响应（旧实现每次「测试连接」泄漏一个连接池）

### ✅ 11. 章节范围反转区间静默只抓 1 章

`源码/爬虫.py` — `run()` 的 `chapter_range` 过滤

`--start 10 --end 3` 经 `end_idx = max(end_idx, start_idx + 1)` 兜底后静默变成「只抓 1 章且不报错」。
现显式规整为 `3~10` 并打告警日志，同时把非正起始序号抬到 1。

### ✅ 12. `_resolve_unique_title` 的 TOCTOU

`源码/爬虫.py`

「读进程级注册表」与「登记注册表」原本分两次加锁 → 两个并发同名任务各自扫到相同 used 集、
算出**同一个** resolved、双双登记 → 后启动者覆盖先写盘的输出文件（进度全丢）。
现把读注册表 + 决策 + 登记合并进同一临界区。

### ✅ 13. 【本轮新发现】dns_doh 的「原函数备份」可指向补丁自身

`源码/dns_doh.py` — `install()`

```python
_orig_getaddrinfo = socket.getaddrinfo     # 旧: 备份的是"调用那一刻"的值
```

若调用 `install()` 时 `socket.getaddrinfo` **已被替换**，备份就指向 `_patched_getaddrinfo`
→ 补丁函数调用自己 → **每一次 DNS 解析 RecursionError**。这不是理论问题：任何模块
`import 爬虫` 都会在导入期调用 `install()`，测试文件的导入顺序一变就会踩中。
现改为固定引用模块导入时快照的 `_真实_getaddrinfo`，并用 `globals().get` 读状态
（有测试会 `del` 掉该全局，直接读会 AttributeError）。

**这个缺陷此前被「测试文件的导入顺序」掩盖**，代价是把同进程的远控 uvicorn 用例一起拖挂
（绑定端口同样要走 getaddrinfo）——本次一度出现「4 个 RecursionError + 1 个远控失败」的假象，
根因只有这一个。同时修正 `测试/test_dns_doh.py`：setUp 不再拿 `socket.getaddrinfo` 当原函数，
tearDown 由 `del` 改为还原（`del` 会让后续 `install()` 抛 AttributeError）。
